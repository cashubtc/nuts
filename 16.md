# NUT-16: Animated QR codes

`optional`

---

This NUT specifies how wallets send and receive Cashu tokens using static and animated QR codes. Token serialization is defined in [NUT-00][00].

## Introduction

Tokens that fit within a single QR symbol can be displayed statically. Larger tokens can be transferred using animated QR codes. Binary fountain encoding splits binary token bytes into frames, encodes each frame as Base45 text in QR alphanumeric mode, and allows receivers to reconstruct the token from a sufficient set of received frames.

## Static QR codes

Senders SHOULD display a serialized text token as a static QR code when it fits the selected QR size and error-correction level, for compatibility with wallets that do not support fountain frames. Fit depends on the encoded byte length, including the mint URL, memo, witnesses and secrets; proof count alone does not determine fit.

A binary fountain transfer with one source fragment MUST use the same frame format as a multipart transfer. Its first frame has sequence number 1 and fragment count 1 and MAY be displayed statically. The frame uses the same Base45 QR encoding described below. Bare `crawB` binary tokens MUST NOT be sent or accepted as NUT-16 QR payloads.

## Transport selection

Wallets implementing this NUT SHOULD support binary fountain encoding for sending and receiving animated QR codes. Automatic capability negotiation is outside the scope of this NUT.

Scanned text beginning with `D+9` MUST be routed to the fountain parser. These three Base45 characters encode the two-byte magic `NF` (`4e 46`), independently of the version and flags. Receivers MUST NOT fall back to token or UR parsing if Base45 decoding or frame validation fails. Other text is processed using the text-token or UR parser, as appropriate.

After Base45 decoding, receivers MUST validate the version and flags bytes. The fountain format version is `01`, and the flags byte MUST be `00`. Frames with an unsupported version or nonzero flags MUST NOT be accepted as this format. Receivers SHOULD report an unsupported format when they recognize the magic but do not support the version. The fountain format version is independent of the NUT-00 token version.

Senders SHOULD offer a way to switch to UR for receivers that do not support fountain frames.

### UR transport

Binary fountain encoding is an alternative to the [UR][ur]-based animated QR transport. Wallets SHOULD continue to support UR for compatibility with wallets that do not support binary fountain frames.

A sender MAY encode a serialized Cashu token using UR and display it as an animated QR code. UR transfers MUST use type `bytes`, with a CBOR byte string containing the UTF-8 serialized text token (for example, `cashuB...`), rather than a `crawB` binary token. The receiver scans frames until its UR decoder reconstructs the token. Senders SHOULD render UR text in uppercase to use QR alphanumeric mode.

## Binary fountain encoding

### Message and notation

The fountain layer transports opaque bytes. For a Cashu transfer under this NUT, the message `M` MUST be the complete NUT-00 V4 binary token:

```text
M = UTF8("crawB") || CBOR(token_v4_object)
```

When converting an existing `cashuB` text token, the sender MUST base64url-decode its body and prepend `crawB`, preserving the original CBOR bytes. The sender MUST NOT include a URI prefix, base64url text, a UR byte-string wrapper or a Bytewords encoding in `M`. This Cashu payload mapping supports V4 tokens only; that restriction is separate from the fountain format version.

| Symbol | Meaning                                                  |
| ------ | -------------------------------------------------------- |
| `L`    | Original message length in bytes, before padding.        |
| `S`    | Source fragment size in bytes.                           |
| `N`    | Source fragment count.                                   |
| `F[i]` | Source fragment at zero-based index `i`.                 |
| `q`    | Frame sequence number, starting at 1.                    |
| `c[i]` | Selection coefficient: 1 includes `F[i]`, 0 excludes it. |
| `C`    | CRC-32 of the original message.                          |
| `P`    | Encoded fragment payload, exactly `S` bytes.             |

### Bounds and fragmentation

The following bounds apply to the fountain format:

| Quantity                    | Allowed values                         |
| --------------------------- | -------------------------------------- |
| Fragment size `S`           | 1 through 4096 bytes                   |
| Source fragment count `N`   | 1 through 1024                         |
| Original message length `L` | 0 through 1,048,576 bytes              |
| Sequence number `q`         | 1 through 4,294,967,295 (`0xffffffff`) |

The message-length bound is independent of the fragment-count and fragment-size bounds; their product does not increase the 1 MiB message limit.

The sender chooses an actual fragment size `S` such that the Base45 encoding of the complete `S + 24` byte frame fits the selected QR symbol (see QR encoding), then computes:

```text
N = max(1, ceil(L / S))
```

The sender MUST check all bounds before emitting frames; if they cannot be satisfied with the selected size, it MUST choose another size or transport. No default fragment size is prescribed. The chosen `S` is the actual payload size of every frame, even when it exceeds `L`; fragment sizes are not implicitly rebalanced.

For `0 <= i < N` and `0 <= j < S`, source fragments MUST contain:

```text
F[i][j] = M[i*S + j]    if i*S + j < L
F[i][j] = 0            otherwise
```

Thus every source fragment has exactly `S` bytes, and unused tail bytes are zero. Padding is excluded from `L` and from `C = CRC32(M)`. `N`, `L`, `C` and `S` MUST remain constant within a transfer. Changing fragmentation starts a new transfer.

At the fountain layer, an empty message has `L = 0`, `N = 1`, `C = 0` and one all-zero source fragment of `S` bytes. A valid source frame completes that empty transfer. An empty message is not a valid Cashu token and MUST NOT be accepted by the wallet as one.

### Frame layout and checksums

Each QR symbol carries exactly one frame. Multibyte integer fields are unsigned 32-bit integers in big-endian byte order. A frame has exactly `S + 24` bytes:

| Byte offset | Length | Field                         |
| ----------- | ------ | ----------------------------- |
| 0           | 2      | ASCII `NF` (`4e 46`).         |
| 2           | 1      | Fountain format version `01`. |
| 3           | 1      | Reserved flags `00`.          |
| 4           | 4      | Sequence number `q`.          |
| 8           | 4      | Source fragment count `N`.    |
| 12          | 4      | Original message length `L`.  |
| 16          | 4      | Message checksum `C`.         |
| 20          | `S`    | Encoded fragment payload `P`. |
| `20 + S`    | 4      | Frame checksum.               |

`S` is inferred as `frame_length - 24`; it is not a separate header field. Valid frame lengths range from 25 through 4120 bytes, subject to the other bounds and the selected QR capacity.

`C` is the CRC-32 of `M`, excluding padding. The frame checksum is the CRC-32 of every preceding byte in that frame, including the magic, version, flags, header and fragment payload. It excludes the trailing checksum field itself.

Both checksums MUST use CRC-32/ISO-HDLC: polynomial `0x04c11db7` (reflected form `0xedb88320`), initial value `0xffffffff`, reflected input and output, and final XOR `0xffffffff`. The check value for ASCII `123456789` is `0xcbf43926`; the checksum of empty bytes is zero. Checksum integers are stored big-endian despite the reflected CRC computation.

### Deterministic fragment selection

For `1 <= q <= N`, the frame selects only source fragment `q - 1`. These are the systematic frames. Later frames contain the bytewise XOR of a deterministic selection of source fragments.

Selection MUST follow `SELECT(q, N)` below. Define:

- `U32(x) = x modulo 2^32`, yielding an integer from 0 through `2^32 - 1`.
- `ADD32(a, b) = U32(a + b)`.
- `MUL32(a, b) = U32(a * b)`; retain exactly the low 32 bits of the product.
- `SHR(a, k) = floor(a / 2^k)` for unsigned 32-bit `a`; this is a logical, zero-filling right shift.
- Bitwise operations act on 32-bit unsigned bit patterns.

Assignment uses `=`; loop ranges are inclusive.

```text
SELECT(q, N):
    c = N zero bits
    if q <= N:
        c[q - 1] = 1
        return c

    state = q
    for i from 0 through N - 1:
        state = ADD32(state, 0x6d2b79f5)
        a = MUL32(state XOR SHR(state, 15), state OR 1)
        b = MUL32(a XOR SHR(a, 7), a OR 61)
        a = a XOR ADD32(a, b)
        c[i] = (a XOR SHR(a, 14)) AND 1

    if every bit of c is zero:
        c[(q - 1) modulo N] = 1
    return c
```

For each frame, the selector state is initialized to the sequence number `q`. Selection depends only on `q` and the source fragment count `N`. The fallback ensures that every frame selects at least one source fragment. Implementations MUST follow the integer operations and fallback defined in `SELECT(q, N)` exactly.

The payload MUST be:

```text
P[j] = XOR of F[i][j] for all i where SELECT(q, N)[i] = 1
       for each j from 0 through S - 1
```

No coefficient list is transmitted. Receivers reproduce the selection from `q` and `N`. For example, for `N = 4`, sequences 5, 6, 7 and 8 select index sets `[1,3]`, `[0,2,3]`, `[2]` and `[0,1,2,3]`, respectively. Repair frames can repeat selections or be dependent on previously received equations; not every repair frame adds information.

The sender MUST start at sequence 1 and increment by one for each newly generated frame. Senders MAY repeat already generated frames, including the first frame of a one-fragment transfer. Sequence 0 is invalid; sequence numbers MUST NOT wrap or exceed `0xffffffff`. On exhaustion, a sender MUST stop generating frames for that transfer; a new encoder can start a transfer at sequence 1. Receivers MUST NOT require receipt of preceding sequences to interpret a frame.

## QR encoding

The sender MUST encode the complete frame, including its checksum, using [Base45 (RFC 9285)][base45], and display the resulting text as one QR alphanumeric-mode segment. It MUST NOT add a URI or other text prefix, use another text encoding, or display the raw frame in QR byte mode. It MUST NOT use ECI, FNC1 or QR structured append for fountain frames.

Base45 uses the following alphabet in order, with a literal space between `Z` and `$`:

```text
0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ $%*+-./:
```

Two bytes are encoded as three characters; a final unpaired byte is encoded as two characters. For a frame of `B = S + 24` bytes, the encoded character count is:

```text
T = 3 * floor(B / 2) + 2 * (B modulo 2)
```

All version-1 frames with zero flags begin with `D+9V50`, the Base45 encoding of `4e 46 01 00`. Routing uses only `D+9` so that unsupported versions or flags still reach frame validation.

The receiver MUST Base45-decode the complete scanned text to recover one frame and then validate it as specified below. It MUST reject characters outside the alphabet, lengths congruent to 1 modulo 3, three-character groups whose decoded value exceeds 65535, and final two-character groups whose decoded value exceeds 255. Receivers MUST preserve spaces and case; they MUST NOT trim, remove whitespace, or change case before decoding. For this version, the text length MUST be between 38 and 6180 characters inclusive, corresponding to the frame-length bounds. These are format bounds; the selected QR symbol can impose a lower capacity.

A scanner's decoded text is sufficient; access to raw QR bytes is unnecessary. For example, browser `BarcodeDetector` exposes text through `rawValue`. Internal spaces are data, even though valid frame text cannot start or end with a space. A frame decoder consumes one complete decoded frame at a time; concatenated frames MUST NOT be treated as one frame.

The sender MAY choose QR version, error-correction level, mask and display rate to suit the devices. These choices MUST NOT alter the frame bytes. The selected capacity MUST account for the Base45 encoding of the full frame. For example, a version 10-M symbol holds 311 alphanumeric characters, fitting 207 frame bytes and leaving at most 183 fragment bytes after the 24-byte overhead. A sender MUST NOT change fragment dimensions within an active transfer to adapt the display; it MUST restart the transfer instead. No fixed animation rate is required for interoperability.

## Receiver behavior

After Base45 decoding and before accepting a frame as an equation or allocating fountain state from its metadata, a receiver MUST validate the total length, magic, version, flags, frame checksum and dimensions:

```text
25 <= frame_length <= 4120
prefix = 4e 46 01 00
S = frame_length - 24
1 <= q <= 0xffffffff
1 <= N <= 1024
0 <= L <= 1048576
1 <= S <= 4096
N = max(1, ceil(L / S))
```

Dimension arithmetic MUST NOT overflow. Invalid input MUST NOT contribute an equation or establish or change the active transfer tuple. Validation order, error signaling and API return values are implementation choices.

Frames combined into one reconstruction MUST have the same tuple `(N, L, S, C)`. A receiver MUST NOT combine frames with different tuples. Whether it rejects unrelated frames, maintains separate sessions or switches sessions is an application policy.

Receivers MUST tolerate loss, reordering and identical duplicate frames. They MUST derive `SELECT(q, N)` and solve the resulting XOR equations. Duplicate or dependent equations MAY be discarded; receiving `N` frames alone does not establish completion. With `N` independent equations, the source fragments can be uniquely recovered. Implementations MAY use Gaussian elimination or another correct decoding algorithm; no particular solver is required.

Before reporting successful fountain reconstruction, a receiver MUST:

1. Recover the source fragments and concatenate them in index order.
2. Take the first `L` bytes as the candidate message and verify its CRC-32 equals `C`.
3. Verify that every remaining byte through the padded length `N*S` is zero.

A failed message checksum or padding check MUST NOT produce a successful reconstruction. Receivers SHOULD reset the affected transfer after either failure, discarding its accumulated equations before collecting new frames. Removing only the last equation may leave an earlier inconsistent equation in the decoder. Progress reporting remains an implementation choice.

Before reporting a successful Cashu transfer, the receiver MUST additionally validate the `crawB` envelope and parse the NUT-00 token. Invalid or empty token payloads MUST NOT be handed to the wallet as valid tokens, even if fountain reconstruction succeeds. Token recovery does not establish proof validity or spendability.

The sender does not receive an acknowledgement through this transport. Receiver completion, cancellation, timeouts and stopping the animation are local application behavior.

## Security and resource limits

CRC-32 detects accidental corruption; it does not authenticate the sender, message or transfer tuple. Colliding checksums and intentionally inconsistent fragments are possible. The tuple is an accidental-mixup guard, not a unique cryptographic identity. Receivers MUST enforce the format's dimension bounds and MUST NOT trust metadata merely because its CRC is correct. Applications SHOULD bound decoding work and active sessions and support cancellation and expiry of incomplete transfers. The fountain transport provides no authentication or confidentiality; applications requiring either provide it separately. The wallet's normal token validation and redemption rules still apply.

## Test vectors

The machine-readable [NUT-16 test vectors][vectors] provide messages, selected fragment indices, complete frame bytes and invalid inputs. Hexadecimal values represent bytes; `qr_text` is the exact Base45 text for the corresponding `frame_hex`. `fragment_size` is the actual `S`, not a maximum capacity. `mixed_only_recovery_sequences` identifies a sufficient set of listed repair frames for reconstructing a transfer without its systematic frames.

Transfers marked `framing-only` exercise the fountain layer and are not valid Cashu tokens. This includes the valid empty-message transfer. The synthetic V4 token is not spendable. `valid_frames` contains individual frame-validation boundary cases; those entries do not claim that receiving one frame completes the whole transfer. `selection_vectors` checks the selector independently of payloads. For invalid inputs, `reject_at` identifies QR text decoding, frame validation, reconstructed-message validation, or Cashu token validation. Additional Base45 and receiver-session vectors are described in the [test-vector guide][vector-guide].
