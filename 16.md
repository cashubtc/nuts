# NUT-16: Animated QR codes

`optional`

---

This document specifies how wallets transfer Cashu tokens using static and animated QR codes. Token serialization is defined in [NUT-00][00]. The binary fountain format below transports an existing binary token without changing its proofs or token version.

## Motivation

Binary fountain frames reduce the number of QR symbols needed to transfer a token by avoiding both the token's base64url representation and UR's textual framing. For equivalent QR symbol sizes, this can require approximately **50% fewer transmitted frames** than Multipart UR (MUR) carrying a `cashuB` text token in UR text form. Actual savings depend on the token size, QR configuration and frame loss.

## Static QR codes

A serialized text token that fits the selected QR size and error-correction level MAY be displayed as a static QR code. Fit depends on the encoded byte length, including the mint URL, memo, witnesses and secrets; proof count alone does not determine fit.

A binary fountain transfer with one source fragment MUST use the same frame format as a multipart transfer. Its first frame has sequence number 1 and fragment count 1 and MAY be displayed statically. A bare binary token is not a binary fountain frame.

## Transport selection and compatibility

Wallets implementing this revision SHOULD support binary fountain frames for sending and receiving animated QR codes. Wallets SHOULD retain support for the existing [UR][ur] transport and offer it when the receiving wallet does not support binary frames. Existing UR-only readers cannot decode the binary format. This specification does not define automatic capability negotiation between wallets.

Receivers MUST dispatch binary frames by their four-byte `CFP1` prefix. Text tokens and UR strings MUST be handled by their respective parsers. An unknown `CFP` version MUST NOT be interpreted as `CFP1`. The frame version is independent of the NUT-00 token version.

### Existing UR transport

For compatibility, a sender MAY produce a UR animated QR code from a serialized Cashu token. The receiver scans until its UR decoder reconstructs the token, as in the previous version of this NUT. This revision does not change that transport's payload mapping or register a new UR type. Senders SHOULD render UR text in uppercase to use QR alphanumeric mode.

## Binary fountain encoding

### Message

The message `M` MUST be the complete NUT-00 V4 binary token:

```text
M = UTF8("crawB") || CBOR(token_v4_object)
```

When converting an existing `cashuB` text token, the sender MUST base64url-decode its body and prepend `crawB`, preserving the original CBOR bytes. The sender MUST NOT include a URI prefix, base64url text, a UR byte-string wrapper or a Bytewords encoding in `M`. This frame version supports V4 tokens only.

### Fragmentation

Let `L` be the length of `M`, and `C` the maximum number of fragment bytes that fit the selected QR symbol after reserving the 24-byte frame overhead. `C` MUST be positive. The sender computes:

```text
N = ceil(L / C)
F = ceil(L / N)
```

The sender partitions `M` into `N` consecutive fragments of `F` bytes, indexed from 0. The last fragment MUST be padded with zero bytes to length `F`. Padding is excluded from `L` and from the message checksum. The sender MUST check the dimension constraints below before emitting frames; if they cannot be satisfied with the selected capacity, it MUST choose another capacity or transport.

`N`, `L`, the message checksum and `F` MUST remain constant within a transfer. Changing fragmentation starts a new transfer.

### Frame layout

Each QR symbol carries exactly one frame. All integer fields are unsigned 32-bit integers in big-endian byte order. A frame has `F + 24` bytes:

| Byte offset | Length | Field                        |
| ----------- | ------ | ---------------------------- |
| 0           | 4      | ASCII `CFP1` (`43 46 50 31`) |
| 4           | 4      | Sequence number `S`          |
| 8           | 4      | Source fragment count `N`    |
| 12          | 4      | Original message length `L`  |
| 16          | 4      | Message checksum `H`         |
| 20          | `F`    | Fragment data `D`            |
| `20 + F`    | 4      | Frame checksum               |

`H` is the CRC-32 of `M`. The frame checksum is the CRC-32 of every preceding byte in that frame, including the magic, header and fragment data. It excludes the trailing checksum field itself.

Both checksums MUST use CRC-32/ISO-HDLC: polynomial `0x04c11db7` (reflected form `0xedb88320`), initial value `0xffffffff`, reflected input and output, and final XOR `0xffffffff`. The check value for ASCII `123456789` is `0xcbf43926`. Checksum integers are stored big-endian despite the reflected CRC computation.

### Fragment selection

Sequence numbers start at 1. For `1 <= S <= N`, `D` MUST equal source fragment `S - 1`. Subsequent frames contain the bytewise XOR of a deterministic set of source fragments.

Fragment selection MUST follow the consensus stack in section 4 of the pinned [Multipart UR implementation guide][mur]. In particular:

- The PRNG seed is `uint32_be(S) || uint32_be(H)`.
- SHA-256 expands the seed for Xoshiro256**.
- The degree distribution has weights `1 / d` for `d` from 1 through `N`, sampled using the guide's alias method.
- The same PRNG is used to shuffle fragment indices; the first `d` indices are selected.
- Implementations MUST preserve the specified PRNG state initialization, random-number consumption, floating-point behavior and shuffle procedure. A different PRNG or shuffle is not interchangeable.

The [test vectors][vectors] include the selected indices and resulting frame bytes. This NUT reuses MUR fragment selection, but replaces its part serialization and text envelope. `CFP1` frames are not UR strings or MUR CBOR parts.

Senders SHOULD transmit the `N` systematic frames first and then emit increasing sequence numbers so that a receiver joining midway can recover from mixed frames. Senders MAY repeat frames. Sequence 0 is invalid; senders MUST stop or restart at sequence 1 after `0xffffffff`, rather than wrap to 0. A one-fragment transfer MAY simply repeat its first frame.

## QR encoding

The sender MUST encode the complete frame as one QR byte-mode segment with the exact frame bytes. It MUST NOT convert the frame to text, hexadecimal, base64url or Bytewords, or add a URI prefix. It MUST NOT use ECI, FNC1 or QR structured append for binary frames.

The receiver MUST obtain the byte-segment payload unchanged, including zero bytes and bytes that are not valid UTF-8. A scanner's decoded text is insufficient. QR codewords containing QR headers, padding or error-correction data are not the payload. Receivers MUST reject symbols containing additional segments or control modes for this binary profile.

The sender MAY choose QR version, error-correction level, mask and display rate to suit the devices. These choices MUST NOT alter the frame bytes. The selected capacity MUST account for the full frame. For example, a version 10-M symbol holds 213 byte-mode payload bytes, leaving at most 189 fragment bytes. A sender MUST NOT change fragment dimensions within an active transfer to adapt the display; it must restart the transfer instead. No fixed animation rate is required for interoperability.

## Receiver behavior

Before adding a frame to a decoder or allocating storage from its metadata, a receiver MUST validate its magic, frame checksum and dimensions:

```text
1 <= S <= 0xffffffff
1 <= N <= 4096
1 <= L <= 1048576
1 <= F <= 1048576
(N - 1) * F < L <= N * F
frame_length = F + 24
```

Dimension arithmetic MUST NOT overflow. These bounds are limits for this frame version; receivers MAY enforce lower resource limits and MUST fail cleanly when a transfer exceeds them.

The first accepted frame establishes the transfer tuple `(N, L, H, F)`. A receiver MUST NOT combine frames with different tuples. It MAY ignore unrelated frames or offer an explicit reset to start a different transfer. A malformed frame MUST NOT establish or change the active tuple.

Receivers MUST tolerate loss, reordering and identical duplicate frames. They MUST determine the selected fragment indices from `S`, `N` and `H`, then solve the resulting XOR equations. Duplicate or dependent equations do not necessarily provide new information; receiving `N` frames alone does not establish completion. Implementations MAY use subset reduction, Gaussian elimination or another correct decoding algorithm. There is no required decoder implementation.

Once every source fragment is recovered, the receiver MUST concatenate them in index order, truncate to `L` bytes and verify the message checksum. It MUST then validate the `crawB` envelope and parse the NUT-00 token before handing it to the wallet. Checksum failure, inconsistent equations or an invalid token MUST NOT produce a successful transfer. A receiver SHOULD discard a failed transfer and permit the user to restart. Token recovery does not establish proof validity or spendability.

The sender does not receive an acknowledgement through this transport. Receiver completion and stopping the animation are local application behavior.

## Security and resource limits

CRC-32 detects accidental corruption; it does not authenticate the sender, message or transfer tuple. Colliding checksums and intentionally inconsistent fragments are possible. Receivers MUST bound memory, decoding work and active sessions, and MUST NOT trust metadata merely because its CRC is correct. Applications SHOULD support cancellation and expiry of incomplete transfers. The wallet's normal token validation and redemption rules still apply.

## Test vectors

The machine-readable [NUT-16 test vectors][vectors] provide message bytes, selected fragment indices, complete frame bytes and invalid inputs for checking implementations. Hexadecimal values represent bytes, not QR text. Transfers marked `framing-only` exercise the fountain layer and MUST NOT be accepted as Cashu tokens. The synthetic V4 token is not spendable. `reject_at` identifies whether an invalid input fails frame validation or reconstructed-message validation.
