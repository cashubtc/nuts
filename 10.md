# NUT-10: Spending conditions

`optional`

`used in: NUT-11, NUT-14, NUT-28`

---

An ordinary ecash token is a set of `Proofs` each with a unique string `secret`. To spend such a token in a [swap][03] or a [melt][05] operation, wallets include `proofs` in their request. To authorize a transaction, the mint requires that the `secret` has not been seen before. This is the most fundamental spending condition in Cashu, which ensures that a token can't be double-spent.

This NUT defines two spending condition families, selected by the proof's keyset version ([NUT-02][02]):

| Keyset version | Secret format                                                                |
| -------------- | ---------------------------------------------------------------------------- |
| `02` and later | a public key: [Nutroot secrets](#nutroot-secrets-v3-keysets)                 |
| `00`, `01`     | random string, or the [well-known JSON Secret](#json-secrets-pre-v3-keysets) |

Mints **MUST** reject any non-point secret on version `02` and later keysets. On earlier keysets a point-shaped string is just another random string, spent under the old rules: the keyset version alone selects which rules apply, never the secret's shape.

## Nutroot secrets (v3 keysets)

For keysets with version byte `02` or later, `Proof.secret` is a single compressed secp256k1 public key (33 bytes, SEC1), encoded as 66 lowercase hex characters. Blind signing treats the secret as opaque bytes: `Y` is computed over the decoded 33 bytes by the keyset version's hash-to-curve (`hash_to_curve_G1` for `02`, [NUT-00][00]).

A proof without spending conditions uses a bare (untweaked) key. The owner holds the keypair `(k, K = k*G)`:

```
secret = K
```

A proof with spending conditions commits them into the key, following [BIP341](https://github.com/bitcoin/bips/blob/master/bip-0341.mediawiki)'s construction with Cashu tags. The secret is the tweaked key:

```
secret = P = K + t*G,  where  t = tagged_hash("Cashu_NutrootTweak", K || merkle_root)
```

`K` is the **internal key** (33-byte compressed) and `merkle_root` commits to a tree of [condition leaves](#condition-leaves). `tagged_hash` is BIP340's construction, `SHA256(SHA256(tag) || SHA256(tag) || message)`, over the tag's UTF-8 bytes. The tweak `t` is used mod the curve order `n`, never rejected: a digest at or above `n` reduces (BIP341 rejects such tweaks instead).

A secret has two spend paths, as in BIP341: the **key path**, a signature by the secret's own scalar, and the **script path**, which reveals one leaf of the tree with its merkle path and satisfies that leaf. [Witnesses](#witnesses) gives the encodings.

A bare `K` and a tweaked `P` are indistinguishable on the wire, and a key-path spend of a locked proof is byte-identical to a bare-key spend: the mint learns of conditions, including their existence, only when a script path is exercised. By default that disclosure ends at the mint; a leaf carrying `disclosure` intentionally makes its exercised witness public through [NUT-07][07] and [NUT-17][17].

### The internal key

`K` takes one of three forms:

- A **single-party** key: its holder can key-path spend, and without conditions it is the secret, untweaked.
- An **aggregated** key (MuSig2, FROST: nobody holds its scalar) **MUST** carry at least the empty tweak `t = tagged_hash("Cashu_NutrootTweak", K)`, no merkle root bytes, even when scriptless: cosigners can then verify no script path is hidden.
- A **NUMS offset** key makes the secret **script-only** (unspendable via key path): BIP341's NUMS point `H` offset by a fresh random scalar.

  ```
  H = 0250929b74c1a04954b78b4b6035e97a5e078a5a0f28ec96d547bfee9ace803ac0
  K = H + u*G          u: a fresh 32-byte random scalar per proof
  ```

  `H` **MUST** be `lift_x(SHA256(G_uncompressed))`: SHA-256 over G's **65-byte uncompressed** SEC1 encoding, taken as an x-coordinate.

  `u` **MUST** be fresh per proof and **MUST** be disclosed in [spend info](#spend-info); holders verify `K - u*G == H`. Seeded wallets **MAY** derive it from the proof's counter instead ([NUT-13][13] type `0x02`). The offset keeps `H`'s unspendability (`dl(H) = dl(K) - u`) and makes each secret unique.

  A NUMS offset `K` is never ECDH-blinded ([NUT-28][28]): nobody holds `H`'s scalar for the receiver's half of the DH.

### TLV encoding

Leaf bodies and the [transaction transcript](#the-transaction-transcript) share one record shape:

```
record = type (1 byte) || length (2 bytes, big-endian) || value
```

Integers encode as minimal big-endian bytes: zero encodes to zero bytes, and a leading zero byte is non-canonical and **MUST** be rejected. There are two stream kinds:

- **Field streams** (a leaf body; the fields inside a transcript container): record types **MUST** strictly ascend.
- **Container streams** (the transcript's top level): container types repeat, one record per element. Containers are grouped in ascending type order (inputs before outputs by construction) and elements keep request order within their type.

### Condition leaves

A serialized leaf is:

```
leaf = leaf_version (1 byte) || leaf_type (1 byte) || field TLVs
```

That exact byte string is the leaf everywhere: in spend info, in a witness, and as the hash preimage. Leaf version `0x00` is the declarative family defined here; all other versions are reserved and **MUST** be treated as unsatisfiable.

The field vocabulary of version `0x00` (allocated types are even; odd types are reserved):

| Field        | Type   | Value                                                                                   |
| ------------ | ------ | --------------------------------------------------------------------------------------- |
| `n`          | `0x02` | signature threshold, 1 byte                                                             |
| `keys`       | `0x04` | concatenated 33-byte compressed public keys, one record                                 |
| `time`       | `0x06` | unix seconds, minimal big-endian, at most `2^53 - 1`                                    |
| `hash`       | `0x08` | SHA-256 digest, 32 bytes                                                                |
| `disclosure` | `0x0a` | one-byte mode: `0x01` publishes the exercised witness via [NUT-07][07] and [NUT-17][17] |

- An unknown field **MUST** be rejected. Odd type numbers are never allocated as ordinary fields: they are reserved for a possible future ignorable-annotation class, and until that class is defined an odd field is unknown like any other.
- A known field on the wrong leaf type is malformed and **MUST** be rejected.

The leaf types of version `0x00`:

| Leaf        | Type   | Fields                             | Satisfied by                                                            |
| ----------- | ------ | ---------------------------------- | ----------------------------------------------------------------------- |
| `threshold` | `0x01` | `n`, `keys`, `disclosure?`         | signatures by `n` distinct listed keys                                  |
| `after`     | `0x02` | `n`, `keys`, `time`, `disclosure?` | verifier's clock >= `time`, plus signatures by `n` distinct listed keys |
| `hashlock`  | `0x03` | `n`, `keys`, `hash`, `disclosure?` | preimage of `hash`, plus signatures by `n` distinct listed keys         |

Types `0x04` and above are unallocated but reserved. An unknown leaf type **MUST** be treated as unsatisfiable, disabling only that path of that proof. New types are allocated in this document and never reinterpreted.

Leaf validation, enforced when building **and** when verifying a disclosed tree:

- `n` **MUST** be at least 1 and at most the number of listed keys.
- `keys` **MUST** list at least one valid compressed secp256k1 point; two keys sharing an x-coordinate are one signer counted twice and **MUST** be rejected.
- A leaf body (the bytes after `leaf_version`) **MUST NOT** exceed 512 bytes, so a serialized leaf is at most 513 bytes.
- `disclosure`, when present, **MUST** be mode `0x01`, serialized as `0a000101`; when absent, the record is omitted. `0x00` and all unallocated modes **MUST** be rejected, preserving one encoding for private leaves while reserving modes for future disclosure policies. It does not affect satisfaction. A mint supporting [NUT-07][07] or [NUT-17][17] **MUST** publish the exact witness and input digest when a mode-`0x01` leaf is exercised. A protocol relying on publication **MUST** verify from [spend info](#spend-info) that no spend path available to the claimant, including the key path, can avoid it.

Multisig is a `threshold` leaf; a refund is an `after` leaf naming the refund keys; an HTLC is a `hashlock` leaf. Combinations are multiple leaves in one tree, and only the exercised leaf is ever revealed. There is no keyless hashlock: a preimage alone is never spend power.

### The tree

```
leaf_hash = tagged_hash("Cashu_NutrootLeaf", serialized_leaf)
branch    = tagged_hash("Cashu_NutrootBranch", min(h1, h2) || max(h1, h2))
```

The merkle root of a single leaf is its leaf hash. For more leaves, the fold is normative: sort the leaf hashes ascending (lexicographic byte order), then pairwise per level, an unpaired last hash promoted to the next level unchanged, until one hash remains.

Duplicate leaves are permitted; the fold **MUST NOT** deduplicate. See the [test vectors][tests] for a worked fold, including the promoted odd leaf and a duplicate pair.

A merkle path is the list of sibling hashes from the leaf to the root; sorted-pair hashing means no left/right flags exist. A tree **MUST NOT** contain more than 8 leaves. Under the normative fold, a valid tree therefore has paths of at most 3 sibling hashes. A tree with more than 8 leaves **MUST** be rejected outright, even if promotion gives some leaves shorter paths.

> [!NOTE]
> The 512-byte leaf-body and 8-leaf caps limit current trees to 120 leaf keys, within [NUT-28][28]'s 255 leaf-key slots. Any future increase to either cap **MUST** remain within those 255 slots or revise NUT-28's slot encoding.

### The transaction transcript

Every v3 spending operation is a transaction with an input section (value sources) and an output section (value sinks):

- **inputs**: proofs, and paid mint quotes
- **outputs**: blinded messages, and melt quotes

Today's operations are instances of this shape on their existing endpoints: mint ([NUT-04][04]) is quote inputs to blinded outputs, swap ([NUT-03][03]) is proof inputs to blinded outputs, melt ([NUT-05][05]) is proof inputs to a melt quote output plus blank change outputs ([NUT-08][08]).

A transaction has one shared digest, and each input derives its own message to sign from it:

```
transaction_digest = SHA256("Cashu_Transaction_v1" || TLV transcript)
input_id           = SHA256(input container record)
input_digest       = tagged_hash("Cashu_TransactionInput", transaction_digest || input_id)
```

The domain tag is the ASCII bytes, plainly prefixed. `input_id` hashes the input's complete outer container record: its one-byte type, two-byte length, and nested field bytes—byte-identical to its appearance in the transcript. A transaction **MUST NOT** contain the same proof `Y` or mint quote id more than once. Subject to SHA-256 collision resistance, no two inputs of a valid transaction sign the same message, and a witness verifies only at its own input. The transcript is one TLV container record per element:

| Container              | Type   | Fields (nested TLV)                                |
| ---------------------- | ------ | -------------------------------------------------- |
| proof input            | `0x01` | `01` amount, `02` keyset id, `03` secret, `04` `C` |
| mint quote input       | `0x02` | `01` amount, `02` quote id                         |
| blinded message output | `0x03` | `01` amount, `02` keyset id, `03` `B_`             |
| melt quote output      | `0x04` | `01` amount, `02` quote id                         |
| authorized request     | `0x05` | `01` method, `02` target, `03` body hash           |

Ordering follows the [TLV encoding](#tlv-encoding) rules for container streams. Element encodings:

- amounts: minimal big-endian
- points (`secret`, `C`, `B_`): raw bytes (BLS points fit without special cases)
- keyset ids: raw bytes when hex; UTF-8 bytes otherwise (compat for pre-NUT-02 base64 ids some implementations still accept)
- quote ids: UTF-8 bytes
- pre-v3 input secrets: UTF-8 bytes (mixed transactions carry them beside v3 inputs)
- method: the HTTP method, uppercase ASCII bytes
- target: the origin-form request-target as sent (the path, plus the query if present), UTF-8 bytes
- body hash: `SHA256` over the exact request body bytes; a request without a body hashes the empty byte string

Quote and output binding:

- A mint quote input binds its quote id and the quote's `amount` as quoted, its face value, never the amount this transaction draws: the output section already binds the draw, so a partial mint ([NUT-04][04]) signs the same face amount on every request. A quote with no fixed amount (eg an onchain quote, [NUT-30][30]) commits amount `0`.
- A melt quote binds its quote id and its `amount`; the fee reserve is not part of the transcript, and [NUT-05][05]'s requirement that inputs cover at least `amount + fee_reserve + fee` is unchanged.
- Outputs are bound exactly as they appear in the request, including blank change outputs.

A transaction **MUST** have at least one input and at least one output. The authorized-request container never appears in a transaction: it is the sole container of a **request transcript**, whose digest is signed directly under this same domain tag by a blind authentication token (an authorized request is not a transaction input) ([NUT-22](22.md#nutroot-blind-authentication-v3-keysets)).

### The signing rule

**Inputs sign; outputs never do.** Every v3 input **MUST** carry a witness containing a BIP-340 Schnorr signature over its [input digest](#the-transaction-transcript):

- each proof input signs with its secret's key,
- each mint quote input signs with its quote lock key ([NUT-04][04]).

Verification is per input. Pre-v3 inputs in the same transaction keep their own rules (the [well-known Secret](#well-known-secret), [NUT-11][11], [NUT-14][14]), so transactions mixing keyset versions are valid. `SIG_ALL`, `sigflag`, and NUT-11's shared-secret rules do not exist for v3 inputs: inputs with different locks, or none, mix freely. (NUT-11's own same-kind, same-flag, same-tags requirement already keeps a pre-v3 `SIG_ALL` input out of any mixed transaction.)

### Witnesses

`Proof.witness` is a serialized JSON string, as in [NUT-11][11]. v3 proofs in serialized tokens **MUST NOT** carry a witness, and wallets **MUST** drop one when encoding or decoding a token: a witness signs its own input digest in a single transaction, so it authorizes nothing anywhere else.

#### Key path

```json
{ "signatures": ["<128-char hex BIP-340 signature>"] }
```

One signature over the input digest by the secret's key: `k` for a bare secret, or `p' = (k + t) mod n` for a tweaked one (since `P = (k + t)*G`). `signatures` **MUST** contain exactly one entry, checked against the secret's x-coordinate. The two cases are byte-identical on the wire.

#### Script path

```json
{
  "leaf": "<serialized leaf, hex>",
  "control": { "K": "<33-byte hex>", "path": ["<32-byte hex>", ...] },
  "signatures": ["<128-char hex>", ...],
  "preimage": "<hex>" // hashlock leaves only
}
```

The presence of `leaf` selects script-path verification. The verifier **MUST**:

1. Reject a `path` containing more than 3 sibling hashes.
2. Recompute `leaf_hash -> root` through `path`, then the tweak from `K` and the root, and check that `K + t*G` equals the secret; otherwise reject.
3. Parse the leaf, failing closed on any unknown version, type, or field.
4. Evaluate the leaf: for `after`, check its local clock is at or past `time`; for `hashlock`, check `SHA256(preimage) == hash`, with the preimage at most 32 bytes; then count the distinct listed keys with a valid BIP-340 signature over the input digest and require at least `n`.

Because Schnorr signatures are non-deterministic, thresholds count distinct satisfied keys, not signatures (as in [NUT-11][11]); even so, `signatures` **MUST NOT** hold more entries than the leaf lists keys. Only the exercised leaf is revealed; sibling leaves remain opaque hashes in `path`. Mints **MAY** reject a serialized witness longer than 4096 characters; every valid witness has a compact JSON encoding below this bound.

### Key uniqueness

[NUT-00][00] requires every secret to be unique, and a v3 secret is a key, so uniqueness comes from key derivation:

- **Seed-derived key**: fresh per proof from the wallet seed ([NUT-13][13]).
- **Blinded static key**: derived per output from the receiver's static key ([NUT-28][28]).
- **Random keypair**: generated per proof; the private key is stored, and travels in [spend info](#spend-info) on transfer.
- **NUMS offset** ([script-only](#the-internal-key) proofs): a fresh `u` per proof, so the internal key is unique without anyone holding its scalar.

Whatever the source, uniqueness is a property of the secret, not the key: the same internal `K` under differing trees yields distinct secrets. Wallets **SHOULD** still use a fresh `K` per proof where possible, since a repeated `(K, tree)` pair repeats the secret and script-path spends revealing a shared `K` links their proofs.

> [!NOTE]
> Key-path signatures verify x-only, secret identity does not: `02 || x` and `03 || x` are distinct secrets with separate `Y` and spent-state entries, yet one scalar key-path spends both, and tweaking does not change this relationship. Wallets and protocols **MUST NOT** assume an x-only key identifies one proof or one spent-state entry. Script paths, including auditable locks, bind the exact compressed secret.

Mints cannot detect a reused secret at issuance: outputs are blinded, and two outputs sharing a secret under different blinding factors have different `B_`. It surfaces only when the first spend burns the shared `Y` and every other proof carrying it is refused as already spent ([NUT-00][00]). Wallets **SHOULD** therefore check each new secret against those they have already used.

Key derivations for v3 keysets **MUST** be hardened at every step (or equivalently hash private material): one non-hardened BIP-32 child plus the tree's xpub recovers the parent and every sibling. Watch-only xpub trees have no place for keys that travel.

### Spend info

A token entry for a v3 proof **MAY** carry spend info: everything the next holder needs that the proof itself does not say. In JSON serializations the field is `spend_info`; in a [NUT-00][00] V4 token it is the CBOR map `si` beside the proof fields, with byte-string values:

| JSON   | V4  | Content                                                                     |
| ------ | --- | --------------------------------------------------------------------------- |
| `k`    | `k` | bearer private key, 32 bytes: "here is the key"                             |
| `E`    | `e` | ephemeral public key, 33 bytes: "derive your key" ([NUT-28][28])            |
| `K`    | `i` | internal public key, 33 bytes: the key the secret is built from             |
| `tree` | `t` | array of serialized leaves, in slot order: always full leaves, never hashes |
| `u`    | `u` | NUMS offset, 32 bytes: proves `K = H + u*G` has no key path                 |

- `k` and `E` are mutually exclusive: a proof **MUST NOT** carry both (the re-gift rule below).
- `K` **MUST** be present when a tree is disclosed with neither `k` nor `E` (nothing else conveys it; the control block needs it), **SHOULD** accompany `E` (only the receiver can derive it; third-party leaf signers cannot spend without it), and is redundant with `k` (`K = k*G`).
- `u` **MUST** be present when the internal key is a [NUMS offset](#the-internal-key) (omission is undetectable but fails a [NUT-18](18.md#nutroot-locking-v3-keysets) NUMS request) and **MUST NOT** be present otherwise: it is what lets a holder verify no key path exists.
- Wallets **SHOULD** send receiver-keyed (`E`, [NUT-28][28]) when they hold a static key for the receiver; the bearer `k` is the offline fallback. A derived private key **MUST NOT** be re-gifted as a bearer `k` (the original sender knows the blinding tweak and could recover the receiver's static key): sweep, then send.

A locked proof's owner needs the tree even for key-path spending (the tweak needs the root), so spend info is fund-critical wallet data: storage, token serialization, backups. A proof with no spend info is the self-owned, seed-recoverable case ([NUT-09][09]/[NUT-13][13]).

#### Receive-time verification

On receiving a v3 proof, the wallet **MUST** verify both of the following, and reject on any failure.

**Check 1: The spend info reconstructs the secret.**

A secret commits the tree, so a disclosure that computes the secret is provably complete: no hidden leaf can exist.

The spend info conveys the **internal key** `K`, the key the secret is built from, by whichever route, in order of precedence: **bearer**, `k*G` from `k`; **receiver-keyed**, the key the wallet derives from `E` ([NUT-28][28] slot `0`); **disclosed**, `K` itself. The derived key is authoritative: a disclosed `K` that differs from the key derived from `E` **MUST** reject.

By spend-info shape:

- No spend info: nothing to reconstruct; the self-owned, seed-recoverable case, decided by check 2 alone.
- No `tree`: `K` or its [empty tweak](#the-internal-key) **MUST** equal the secret (a bare key, or the aggregated form).
- A disclosed `tree`:
  - every leaf **MUST** parse (an unknown version, type, or constraint field rejects);
  - `K + t*G` over the recomputed root **MUST** equal the secret;
  - if `u` is present, `K - u*G` **MUST** equal NUMS point `H`: the proof is script-only and no key path exists.
- Anything else, including a tree without a key source: reject.

The fold sorts, so the root commits the leaf set, never the transmitted order: a permuted list reconstructs the same root and **MUST** be treated as equivalent, and nothing may be derived from a leaf's position ([NUT-28][28] value matching).

**Check 2: The wallet can spend it.**

Wallets swapping proofs immediately will enforce this check implicitly.

Wallets receiving offline, or holding a locked proof under its conditions, **MUST** check that they hold the key path (`k`, a key derived from `E`, the seed key of a proof with no spend info ([NUT-13][13]), or a cosigner share of an aggregated `K`), or keys satisfying a disclosed leaf.

A proof the wallet cannot spend, eg an aggregated `K` it does not cosign, **MUST NOT** be treated as received value, and a wallet **MUST** evaluate every disclosed leaf against its acceptance policy (eg a minimum refund horizon) before treating a payment as received.

**Other recommended checks**

Both checks assume the proof is genuine: wallets **SHOULD** verify `C` against the keyset key on receive by the [pairing equality](00.md#pairing-based-bls-blind-signatures), which needs no mint round-trip.

**Sweeping.** Receivers **SHOULD** swap a received proof to their own seed-derived secrets promptly, whatever the spend-info shape:

- bearer `k`: the sender holds the same scalar, and a bearer scalar can conceal a tweaked tree (`p'` and a bare `k` verify identically); sweeping extinguishes both.
- receiver-keyed `E`: the ephemeral is wallet data, not seed-derivable ([NUT-13][13]), so the proof is unrecoverable from the seed alone until swept.
- a disclosed `tree` with neither `k` nor `E`: the key-path holder can spend at any time, unless `K` is a NUMS offset.

### Auditable locks

Nutroot locks are private by default: a receiver-keyed proof is provable only by its key holder. Some payments want the opposite, a lock any third party can read and attest (eg a public tip / Nutzap). The canonical **auditable lock** to a single key `P` is script-only:

- internal key: a [NUMS offset](#the-internal-key) with `u` disclosed;
- tree: exactly one [`threshold`](#condition-leaves) leaf, `n = 1`, `keys = [P]`, with `disclosure`, the key not [blinded](28.md).

Verification needs no keys and no mint: [check 1](#receive-time-verification) over the disclosed `K`, `u` and `tree` proves the secret commits to exactly that leaf and that no key path exists, so `P` and nobody else can spend it. On spend, `disclosure` makes the witness and input digest public, so anyone holding the proof can verify `P`'s signature without learning the shared transaction digest. The disclosure is minimal by construction: the leaf has one canonical serialization, so a holder who knows the candidate key can rebuild the whole spend info from `u` alone (`K = H + u*G`, the tree from `P`) and cross-check what was disclosed, or recover a proof whose spend info was mangled in transit.

Which key to expect is the transport's business (eg a nostr nutzap event naming the recipient); this section only fixes the encoding those transports share.

### Signaling

Support is signaled by the keyset itself: a mint advertising a keyset with version byte `02` or later ([NUT-01][01], [NUT-02][02]) **MUST** implement everything in this section. The `MintMethodSetting`s of NUT-10 (below), [NUT-11][11], [NUT-14][14] and [NUT-20][20] apply only to pre-v3 keysets.

Future leaf types and versions define their own signaling when allocated.

**Note:** See the [test vectors][tests].

## JSON secrets (pre-v3 keysets)

For pre-`02` keysets, this section defines a well-known format of `secret` that expresses more complex spending conditions. These conditions need to be met before the mint authorizes a transaction. The specific types of spending condition are defined in other documents; here we describe the structure of `secret`, expressed as a JSON `Secret` with a specific format.

Spending conditions are enforced by the mint which means that, upon encountering a `Proof` where `Proof.secret` can be parsed into the well-known format, the mint can require additional conditions to be met.

Caution: If the mint does not support spending conditions or a specific `kind` of spending condition, proofs may be treated as a regular anyone-can-spend tokens. Applications need to make sure to check whether the mint supports a specific `kind` of spending condition by checking the mint's [info][06] endpoint.

### Basic components

An ecash transaction, i.e., a [swap][03] or a [melt][05] operation, with a spending condition consists of the following components:

- Inputs referring to the `Proofs` being spent
- `Secret` containing the rules for unlocking a `Proof`
- Additional witness data satisfying the unlock conditions such as signatures
- Outputs referring to the `BlindMessages` with new unlock conditions to which the `Proofs` are spent to

Spending conditions are defined for each individual `Proof` and not on a transaction level that can consist of multiple `Proofs`. Similarly, spending conditions must be satisfied by providing signatures or additional witness data for each `Proof` separately. For a transaction to be valid, all `Proofs` in that transaction must be unlocked successfully.

New `Secret`s of the outputs to which the inputs are spent to are provided as `BlindMessages` which means that they are blind-signed and not visible to the mint until they are actually spent.

### Well-known Secret

Spending conditions are expressed in a well-known secret format that is revealed to the mint when spending (unlocking) a token, not when the token is minted (locked). The mint parses each `Proof`'s `secret`. If it can deserialize it into the following format it executes additional spending conditions that are further specified in additional NUTs.

The well-known `Secret` stored in `Proof.secret` is a JSON of the format:

```json
[
kind <str>,
  {
    "nonce": <str>,
    "data": <str>,
    "tags": [[ "key", "value1", "value2", ...],  ... ], // (optional)
  }
]
```

- `kind` is the kind of the spending condition
- `nonce` is a unique random string
- `data` expresses the spending condition specific to each kind
- `tags` hold additional data committed to and can be used for feature extensions

#### Tag format

The optional `tags` field, is an array of arrays of non-empty strings.

Each individual tag is an array of **ONE or more strings**. The first element of the tag array is known as the tag _name_ or _key_ and the subsequent string(s) are the _tag value(s)_.

**Examples of valid tags:**

`["pubkeys"]` - a tag with the key, `"pubkeys"` and no tag values.\
`["pubkeys", "021..."]` - a tag with the key, `"pubkeys"` and ONE tag value.\
`["pubkeys", "021...", "022..."]` - a tag with the key, `"pubkeys"` and TWO tag values.

**Examples of invalid tags:**

`[]` - a tag array must contain at least **ONE** or more strings\
`["locktime", 1765300829]` - a tag must contain **strings** only\
`["locktime", ""]` - a tag must contain **non-empty strings** only

### Examples

Example use cases of this secret format are

- [NUT-11][11]: Pay-to-Public-Key (P2PK)
- [NUT-14][14]: Hashed Timelock Contracts (HTLCs)
