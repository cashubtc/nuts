# NUT-00: Notation, Utilization, and Terminology

`mandatory`

---

This document details the notation and models used throughout the specification and lays the groundwork for understanding the basic cryptography used in the Cashu protocol.

- Sending user: `Alice`
- Receiving user: `Carol`
- Mint: `Bob`

Cashu uses a blind BLS signature scheme on BLS12-381. Ecash secrets are secp256k1 public keys ([NUT-10][10]), and transactions are signed with Schnorr signatures over that curve ([signing rule](#the-signing-rule)).

# Pairing-based BLS blind signatures

## Groups and Scalars

- `BLS_FR_ORDER` order of the BLS12-381 prime-order subgroup (and of `Fr`)
- `Fr` finite field of integers modulo `BLS_FR_ORDER`; scalars live here.
- `G1`, `G2` BLS12-381 prime-order groups of order `BLS_FR_ORDER` (`Y`, `B_`, `C_`, `C` live in `G1`; `K` lives in `G2`); `G1` points come from `hash_to_curve_G1`.
- `g1`, `g2` fixed generators of `G1`, `G2`

## Notation And Conventions

These specifications use [BLS12-381](https://datatracker.ietf.org/doc/draft-irtf-cfrg-pairing-friendly-curves/), a pairing-friendly curve, with a Type-3 pairing `e: G1 × G2 → G_T`.

### Types

Values are one of:

- Scalars: integers in `Fr` (the prime field of order `BLS_FR_ORDER`)
- G1 points: compressed 48 bytes / 96 hex characters
- G2 points: compressed 96 bytes / 192 hex characters
- Byte sequences

Compressed point encoding follows the standard BLS12-381 serialisation. Hex encodings in JSON fields are lowercase, with no `0x` prefix and the fixed widths above. The identity point (point at infinity) is never a valid blinded message, signature, or mint key.

### Bob (mint)

- `a` private key of mint, scalar in `Fr` (one for each amount)
- `K = a·g2` public key in `G2` corresponding to `a` (compressed 96 bytes)
- `C_` blind signature in `G1` on `B_`

### Alice (user)

- `x` secret bytes (see [Secret bytes](#secret-bytes)), corresponds to point `Y = hash_to_curve_G1(x)` in `G1`
- `r` blinding factor, scalar in `Fr`
- `B_ = r·Y` blinded message in `G1`
- `C` unblinded signature in `G1`

## Protocol

- Mint `Bob` publishes per-amount public key `K = a·g2`
- `Alice` picks secret `x` and computes `Y = hash_to_curve_G1(x)`
- `Alice` sends to `Bob`: `B_ = r·Y` with `r` a random non-zero scalar in `Fr` (**blinding**)
- `Bob` sends back to `Alice`: `C_ = a·B_` (**signing**)
- `Alice` unblinds: `C = r⁻¹·C_ = a·Y` (**unblinding**)
- `Alice` can take the pair `(x, C)` as a token and send it to `Carol`.
- Anyone holding `K` can verify a proof `(x, C)` (**verification**) by computing `Y = hash_to_curve_G1(x)` and accepting only if `e(C, g2) == e(Y, K)`.
- `Carol` can send `(x, C)` to `Bob`, who treats it as a valid spend of a token, adding `x` to the list of spent secrets, if the token verifies and has not been seen before.

### `hash_to_curve_G1(x: bytes) -> G1 point Y`

Maps `x` deterministically to a point in `G1` using the BLS12-381 G1 random-oracle suite defined in [RFC 9380](https://www.rfc-editor.org/rfc/rfc9380) §8.8.1 (`BLS12381G1_XMD:SHA-256_SSWU_RO_`), with Cashu domain separation tag (DST):

```
DST = b"CASHU_BLS12_381_G1_XMD:SHA-256_SSWU_RO_"
```

### Secret bytes

`Proof.secret` is a compressed secp256k1 public key encoded as 66 lowercase hex characters ([NUT-10 Nutroot secrets](10.md#nutroot-secrets-v3-keysets)), and `x` is its **decoded 33 bytes**.

Mints **MUST** reject any other secret form on a [v3 keyset](02.md#keyset-id-v3).

### Optional: Batch Verification

`Bob` (and any other verifier) can verify many proofs in a single multi-pairing.

Constants:

```
BLS_BATCH_DST = b"Cashu_BLS_Batch_v1"
```

For a batch of `n` proofs, each with mint key `K_i`, unblinded signature `C_i`, and secret bytes `secret_i` (the proof's [secret bytes](#secret-bytes), the same bytes fed to `hash_to_curve_G1`):

1. Build a length-prefixed transcript:

```
transcript = BLS_BATCH_DST
for i in 0..n-1:
    transcript ||= C_i.compressed   # 48 bytes
    transcript ||= K_i.compressed   # 96 bytes
    transcript ||= u32_BE(len(secret_i))
    transcript ||= secret_i
```

2. Collapse to a single 32-byte challenge:

```
challenge = SHA256(transcript)
```

3. Derive each per-proof weight `w_i ∈ Fr*` by **rejection sampling**. For `i = 0..n-1`, iterate `ctr = 0, 1, …` until a valid scalar is produced:

```
h = SHA256(challenge || u32_BE(i) || u32_BE(ctr))
x = OS2IP(h)
if x == 0 or x >= BLS_FR_ORDER:
    continue   # try next ctr
w_i = x
```

> [!IMPORTANT]
> Rejection sampling **MUST** be used to avoid bias.

4. Group items by distinct mint key `K_k` and check:

```
e( Σ_i w_i·C_i , g2 ) == Π_k e( Σ_{i:K_i=K_k} w_i·Y_i , K_k )
```

Implementations **SHOULD** evaluate `Π_k e( Σ_{i:K_i=K_k} w_i·Y_i , K_k )` with a single call to a multi-miller loop primitive, at the end of which they **SHOULD** perform the final exponentiation over the accumulated miller loop.

Typical batch scopes:

- A wallet receiving a token batches all v3 proofs across that token.
- A mint batches all v3 input proofs of a single `/v1/swap` or `/v1/melt` request.

A batch of one proof reduces to the single-proof pairing check above.

The weights are public and deterministic; security does not rely on their secrecy.

### Point Validation

Implementations **MUST** deserialise all v3 `B_`, `C_`, `C`, and `K` values using the canonical compressed BLS12-381 encoding, and **MUST** reject:

- non-canonical encodings,
- the identity (point at infinity),
- points not on the curve,
- points not in the prime-order subgroup of `G1` (for `B_`, `C_`, `C`) or `G2` (for `K`).
- points with cofactor components

> [!IMPORTANT]
> Full validation with cofactor rejection is required to defend against the [small-subgroup attack][lim-lee].

# Cashu conventions and models

## General notation and conventions

These specifications use elliptic curve public key cryptography over the field and curve parameters defined by [secp256k1](http://www.secg.org/sec2-v2.pdf).

### Types

Values in these specifications are one of:

- Scalars: integers modulo the curve order `n`
- Curve points: elements of the elliptic curve group (including the identity point at infinity)
- Byte sequences

### Byte Operations And Encodings

- Concatenation `||` appends one byte sequence to another.
- All operations such as point addition, scalar multiplication, hashing, are performed on the underlying mathematical values, not on their serialized byte encodings.
- When a curve point is serialized as `hex_str`, it is the hex encoding of the SEC1 compressed public key bytes, unless a NUT specifies a different encoding.
- Integer byte order and fixed widths are defined by each NUT where relevant, if a NUT is silent, it must not be assumed.

### Hashing

- `SHA256(m)` denotes the SHA 256 hash of byte sequence `m`.
- Any hash to curve function must specify its domain separator and exact procedure, including how counters are encoded and incremented.

## 0.1 - Models

### `BlindedMessage`

An encrypted ("blinded") secret and an amount are sent from `Alice` to `Bob` for [minting tokens][04] or for [swapping tokens][03]. A `BlindedMessage` is also called an _output_.

```json
{
  "amount": int,
  "id": hex_str,
  "B_": hex_str
}
```

`amount` is the value for the requested `BlindSignature`, `id` is the requested keyset ID from which we expect a signature, and `B_` is the blinded secret message generated by `Alice`. An array `[BlindedMessage]` is also referred to as `BlindedMessages`.

`B_` **MUST** be unique across the entire mint: mints **MUST** reject a `B_` they have signed (error `11003`) or hold for a pending operation (error `11004`), per [Error Codes][errors].

### `BlindSignature`

A `BlindSignature` is sent from `Bob` to `Alice` after [minting tokens][04] or after [swapping tokens][03]. A `BlindSignature` is also called a _promise_.

```json
{
  "amount": int,
  "id": hex_str,
  "C_": hex_str
}
```

`amount` is the value of the blinded token, `id` is the [keyset id][02] of the mint keys that signed the token, and `C_` is the blinded signature on the secret message `B_` sent in the previous step.

On v3 keysets, mints **MUST NOT** include a `dleq` field in a `BlindSignature` and wallets **MUST NOT** include one in a `Proof`; receivers **SHOULD** treat a v3 `BlindSignature` or `Proof` carrying `dleq` as malformed. `C` is verified by the [pairing equality](#pairing-based-bls-blind-signatures).

### `Proof`

A `Proof` is also called an _input_ and is generated by `Alice` from a `BlindSignature` it received. An array `[Proof]` is called `Proofs`. `Alice` sends `Proofs` to `Bob` for [melting tokens][05]. [Serialized](#serialization-of-tokens) `Proofs` can also be sent from `Alice` to `Carol`. Upon receiving the token, `Carol` deserializes it and requests a [swap][03] from `Bob` to receive new `Proofs`.

```json
{
  "amount": int,
  "id": hex_str,
  "secret": hex_str,
  "C": hex_str,
  "witness": str, // inputs only
  "spend_info": { ... } // tokens only
}
```

`amount` is the amount of the `Proof`, `secret` is the [nutroot secret][10] as 66 lowercase hex characters, `C` is the unblinded signature on `secret` (hex string), `id` is the [keyset id][02] of the mint public keys that signed the token (hex string). `witness` is the proof's serialized [witness](#witnesses), required on [inputs](#the-signing-rule). `spend_info` is the proof's [spend info](#spend-info), carried in tokens.

A proof on a pre-v3 keyset follows [legacy NUT-00](legacy/00.md#proof).

`secret` **MUST** be unique per `Proof` across the entire mint: each secret maps to a curve point `Y`, and mints **MUST** reject a duplicated `Y` as already spent.

## 0.2 - Protocol

### Errors

In case of an error, mints respond with the HTTP status code `400` and include the following data in their response:

```json
{
  "detail": "oops",
  "code": 1337
}
```

Here, `detail` is the error message, and `code` is the error code. Error codes are to be defined in the documents concerning the use of a certain API endpoint.

## 0.3 - Methods

### Serialization of tokens

Tokens can be serialized to send them between users `Alice` and `Carol`. Serialized tokens have a Cashu token prefix, a versioning flag, and the token. Optionally, a URI prefix for making tokens clickable on the web.

We use the following format for token serialization:

```sh
cashu[version][token]
```

`cashu` is the Cashu token prefix. `[version]` is a single `base64_urlsafe` character to denote the token format version. Version `B` is defined below; version `A` is deprecated ([legacy NUT-00](legacy/00.md#v3-tokens)).

##### URI tags

To make Cashu tokens clickable on the web, we use the URI scheme `cashu:`. An example of a serialized token with URI tag is

```sh
cashu:cashuBo2FtcWh0dHBzOi8vbWludC50ZXN0YXVjc2F0YXSBomFpSAIlRqsKLe6f...
```

### V4 tokens

V4 tokens are a space-efficient way of serializing tokens using the CBOR binary format. All keys are single characters and hex strings are encoded in binary. V4 tokens can only hold proofs from a single mint.

##### Version

This token format has the `[version]` value `B`.

##### Format

Wallets serialize tokens in a `base64_urlsafe` format (base64 encoding with `/` replaced by `_` and `+` by `-`). `base64_urlsafe` strings may have padding characters (usually `=`) at the end which can be omitted. Clients need to be able to decode both cases.

```sh
cashuB[base64_token_cbor]
```

##### Token format

For readability, the structure of a TokenV4 object is shown below in its equivalent JSON form.

```json
{
  "m": str, // mint URL
  "u": str, // currency unit
  "d": str <optional>, // optional memo
  "t": [
    {
      "i": bytes, // keyset ID (short or long form)
      "p": [ // proofs with this keyset ID
        {
          "a": int, // amount
          "s": str, // secret
          "c": bytes, // signature
          "si": { ... } <optional> // spend info
        },
        ...
      ]
    },
    ...
  ]
}
```

`m` is the mint URL. The mint URL **MUST** be normalized by stripping any trailing slashes (`/`). `u` is the currency unit of the token keysets. Supported units are defined in [Keysets][01]. `d` is an optional, human-readable memo provided by the sender.

Within the `t` (token) array, `i` denotes the keyset ID associated with the proofs contained in `p` which are grouped by `i`. `p` is an array of `Proof` objects with the original keyset ID field `id` omitted. All proofs in the corresponding `p` array MUST belong to the same keyset ID.

Unless otherwise stated, fields of type `bytes` represent byte strings in the CBOR encoding. In the original JSON representation of `Proof` objects, these values are encoded as hexadecimal strings. Implementations MUST convert between hex strings and raw byte arrays when translating between JSON and CBOR representations.

`si` is the proof's [spend info](#spend-info). Wallets **MUST** preserve `si` when re-serializing a proof, whether or not they read it. An entry for a proof on a pre-v3 keyset follows [legacy NUT-00](legacy/00.md#v4-tokens).

Optional fields **MAY** be omitted if not present. Receivers **MUST** ignore unknown fields to preserve forward compatibility. Map key order is not significant: encoders **MAY** emit keys in any order and receivers **MUST** accept any order, so encoded tokens are not byte-comparable across implementations.

#### Short keyset ID

To reduce the size of the `i` field and the overall Token encoding, wallets **MAY** use the short keyset ID representation (`s_id`).

The short keyset ID is defined as the first 8 bytes of the full 33-byte keyset ID:

- Byte form: `s_id = id_bytes[:8]`
- Hex form: `s_id = id_hex_str[:16]`

Wallets receiving a Token **MUST** support both short and full keyset ID representations. When a short keyset ID is encountered, the wallet **MUST** resolve it to the corresponding full keyset ID before processing the contained `Proof` objects.

If a short keyset ID resolves to more than one known full keyset ID, the identifier is considered ambiguous. In this case, the wallet **MUST** fail token parsing and return an error.

The mint is unaware of the `s_id`. All API endpoints exposed by the mint use the full keyset ID.

Tokens can be transmitted in a binary format when applicable (for example when transmitting via NFC).

```

```

### Spend info

A token entry for a v3 proof **MUST** carry the spend info its receiver needs to spend it.

In JSON serializations the field is `spend_info`; in a [V4 token](#v4-tokens) it is the CBOR map `si` beside the proof fields, with byte-string values:

| JSON   | V4  | Content                                                             |
| ------ | --- | ------------------------------------------------------------------- |
| `k`    | `k` | bearer private key, 32 bytes: "here is the key"                     |
| `E`    | `e` | ephemeral public key, 33 bytes: "derive your key" ([NUT-28][28])    |
| `K`    | `i` | internal public key, 33 bytes: the key the secret is built from     |
| `tree` | `t` | array of serialized [leaves](10.md#condition-leaves), in slot order |
| `u`    | `u` | NUMS offset, 32 bytes: proves `K = H + u*G` has no key path         |

- `k` and `E` are mutually exclusive: a proof **MUST NOT** carry both.
- `K` **MUST** be present when a tree is disclosed with neither `k` nor `E`, and **SHOULD** accompany `E` so third-party leaf signers can build the control block.
- `tree`, when present, **MUST** hold at least one leaf: an empty array is malformed.
- `u` **MUST** be present when the internal key is a [NUMS offset](10.md#the-internal-key) and **MUST NOT** be present otherwise. `u` without a `tree` is malformed.
- A key derived from `E` **MUST NOT** be sent on as a bearer `k`: sweep, then send.

#### Receive-time verification

On receiving a v3 proof, the wallet **MUST** verify both of the following, and reject on any failure.

**Check 1: The spend info reconstructs the secret.**

The spend info conveys the **internal key** `K`, the key the secret is built from, by whichever route, in order of precedence: **bearer**, `k*G` from `k`; **receiver-keyed**, the key the wallet derives from `E` ([NUT-28][28] slot `0`); **disclosed**, `K` itself. The derived key is authoritative: a disclosed `K` that differs from the key derived from `E` **MUST** reject.

By spend-info shape:

- No spend info: nothing to reconstruct; check 2 decides.
- No `tree`: `K` or its [empty tweak](10.md#the-internal-key) **MUST** equal the secret (a bare key, or the aggregated form).
- A disclosed `tree`:
  - every leaf **MUST** parse (an unknown version, type, or constraint field rejects: the wallet cannot evaluate it), and a `commit` leaf adds no spend path;
  - `K + t*G` over the recomputed root **MUST** equal the secret;
  - if `u` is present, `K - u*G` **MUST** equal NUMS point `H`: the proof is script-only and no key path exists.
- Anything else, including a tree without a key source: reject.

Leaves may be transmitted in any order: a permuted `tree` reconstructs the same root and **MUST** be treated as equivalent.

**Check 2: The wallet can spend it.**

A wallet that swaps on receive enforces this implicitly. Otherwise it **MUST** check that it holds the key path (`k`, a key derived from `E`, the seed key of a proof with no spend info ([NUT-13][13]), or a cosigner share of an aggregated `K`), or keys satisfying a disclosed leaf.

A proof the wallet cannot spend, eg an aggregated `K` it does not cosign, **MUST NOT** be treated as received value, and a wallet **MUST** evaluate every disclosed leaf against its acceptance policy (eg a minimum refund horizon) before treating a payment as received.

Wallets **MUST** verify `C` by the [pairing equality](#pairing-based-bls-blind-signatures) when unblinding and on receive. Wallets **SHOULD** sweep received proofs to their own seed-derived secrets promptly: a bearer `k` is shared with its sender, and an `E`-keyed proof becomes seed-recoverable only once swept.

## 0.4 - Transactions (v3 keysets)

### Tagged hashes

We use BIP340's construction, over the tag's UTF-8 bytes:

```
tagged_hash(tag, message) = SHA256(SHA256(tag) || SHA256(tag) || message)
```

### TLV encoding

Transaction transcripts and [NUT-10](10.md#condition-leaves) leaf bodies share one record shape:

```
record = type (1 byte) || length (2 bytes, big-endian) || value
```

Integers encode as minimal big-endian bytes: zero encodes to zero bytes, and a leading zero byte is non-canonical and **MUST** be rejected. There are two stream kinds:

- **Field streams** (a leaf body; the fields inside a transcript container): record types **MUST** strictly ascend.
- **Container streams** (the transcript's top level): container types repeat, one record per element. Containers are grouped in ascending type order and elements keep request order within their type.

### The transaction transcript

Every spending operation is a transaction with an input section (value sources) and an output section (value sinks):

- **inputs**: proofs, and paid mint quotes
- **outputs**: blinded messages, and melt quotes

Today's operations are instances of this shape on their existing endpoints: mint ([NUT-04][04]) is quote inputs to blinded outputs, swap ([NUT-03][03]) is proof inputs to blinded outputs, melt ([NUT-05][05]) is proof inputs to a melt quote output plus blank change outputs ([NUT-08][08]).

A transaction **MUST** have at least one input and at least one output, and **MUST NOT** contain the same proof `Y` or mint quote id more than once.

The TLV transcript serializes the transaction, one TLV container record per element:

| Container              | Type   | Fields (nested TLV)                                    |
| ---------------------- | ------ | ------------------------------------------------------ |
| proof input            | `0x11` | `01` amount, `02` keyset id, `03` `Y`, `04` `C`        |
| mint quote input       | `0x12` | `01` amount, `02` quote id, `03` lock key, `04` issued |
| blinded message output | `0x21` | `01` amount, `02` keyset id, `03` `B_` hash            |
| melt quote output      | `0x22` | `01` amount, `02` quote id                             |
| authorized request     | `0xF1` | `01` method, `02` target, `03` body hash               |

The high nibble of a container type is its section: `0x1n` inputs, `0x2n` outputs, and `0xFn` containers outside transactions (eg a [NUT-22](22.md#nutroot-blind-authentication-v3-keysets) request transcript), which **MUST NOT** appear in a transaction.

Ordering follows the [TLV encoding](#tlv-encoding) rules for container streams. Element encodings:

- amounts and `issued`: minimal big-endian
- points (`Y`, `C`): raw bytes
- keyset ids: decoded from hex when the id is an even-length string of hex digits; the UTF-8 bytes of the string otherwise
- quote ids: UTF-8 bytes
- lock keys: 33-byte compressed secp256k1 public keys, raw bytes
- `Y`: the keyset's `hash_to_curve` of the proof's secret: [secret bytes](#secret-bytes) for a v3 proof, [legacy NUT-00](legacy/00.md#hash_to_curvex-bytes---curve-point-y)'s for a pre-v3 one
- `B_` hash: `SHA256` over the blinded message's compressed point, after [point validation](#point-validation)

Quote and output binding:

- A mint quote input binds its quote id, its lock key, which **MUST** equal the quote's `pubkey` ([NUT-04][04]), the amount this transaction issues against the quote, which **MUST NOT** exceed the quote's mintable amount, `amount_paid - amount_issued`, and `issued`, the quote's `amount_issued` when the mint accepts the transaction, read from the mint's own quote state and present even when zero. A quote input's witness therefore authorizes one issuance from its quote.
- A melt quote output binds its quote id and the quote's `amount` plus the fee reserve the request selects: the quote's `fee_reserve`, or for a quote offering `fee_options` ([NUT-30][30]) the entry its `fee_index` names, read from the mint's own quote state.
- Outputs are bound exactly as they appear in the request, including blank change outputs.

Each input signs its own digest:

```
transaction_digest = SHA256(TLV transcript)
input_id           = SHA256(input TLV container record)
input_digest       = tagged_hash("Cashu_TransactionInput", transaction_digest || input_id)
```

`input_id` hashes the input's complete outer TLV container record (type, length and nested fields), byte-identical to its appearance in the transcript.

### The signing rule

**Inputs sign.** Every v3 input **MUST** carry a witness containing a BIP-340 Schnorr signature over its [input digest](#the-transaction-transcript):

- each proof input signs with its secret's key,
- each mint quote input signs with its quote lock key ([NUT-04][04]), by key path or [script path](10.md#script-path) as a proof does.

Verification is per input, and pre-v3 inputs keep their own rules (the [well-known Secret](legacy/10.md#well-known-secret), [NUT-11][11], [NUT-14][14]), so keyset versions mix in one transaction. NUT-11's `SIG_ALL` and `sigflag` apply only to pre-v3 inputs.

### Witnesses

A witness is a serialized JSON object with no canonical encoding:

```json
{
  "signatures": ["<128-char hex BIP-340 signature>", ...],
  // Additional fields may be added (eg: NUT-10 script path)
}
```

The [NUT-10 script path](10.md#script-path) defines the other optional fields; a witness without `leaf` is a key-path witness.

A proof's [`witness`](#proof) is always the object. A mint quote's `signature` field ([NUT-04](04.md#nutroot-transactions-v3-keysets)) also accepts a key-path witness as the bare 128-character hex signature.

v3 proofs in serialized tokens **MUST NOT** carry a `witness`, and wallets **MUST** drop one when encoding or decoding a token.

#### Key path

One signature over the input digest by the secret's key: `k` for a bare secret, or `p' = (k + t) mod n` for a [tweaked](10.md#nutroot-secrets-v3-keysets) one. `signatures` **MUST** contain exactly one entry, checked against the secret's x-coordinate.

Key-path signatures verify x-only, so `02 || x` and `03 || x` are distinct secrets with separate spent-state entries that one scalar spends.
