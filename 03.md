# NUT-03: Swap tokens

`mandatory`

---

The swap operation is the most important component of the Cashu system. A swap operation consists of multiple inputs (`Proofs`) and outputs (`BlindedMessages`). Mints verify and invalidate the inputs and issue new promises (`BlindSignatures`). These are then used by the wallet to generate new `Proofs` (see [NUT-00][00]).

The swap operation can serve multiple use cases. The first use case is that `Alice` can use it to split her tokens to a target amount she needs to send to `Carol`, if she does not have the necessary amounts to compose the target amount in her wallet already. The second one is that `Carol`'s wallet can use it to receive tokens from `Alice` by sending them as inputs to the mint and receive new outputs in return.

## Swap to send

To make this more clear, we present an example of a typical case of sending tokens from `Alice` to `Carol`.

`Alice` has 64 sat in her wallet, composed of three `Proofs`, one worth 32 sat and another two worth 16 sat. She wants to send `Carol` 40 sat but does not have the necessary `Proofs` to compose the target amount of 40 sat. For that, `Alice` requests a swap from the mint and uses `Proofs` worth `[16, 16, 32]` as inputs and asks for new outputs worth `[8, 32, 8, 16]` totaling 64 sat. Notice that the first two tokens can now be combined to 40 sat. The `Proofs` that `Alice` sent `Bob` as inputs of the swap operation are now invalidated.

Note: In order to preserve privacy around the amount that a client might want to send to another user and keep the rest as change, the client **SHOULD** ensure that the list of requested outputs is ordered by amount in ascending order. As an example of what to avoid, a request for outputs expressed like so: `[16, 8, 2, 64, 8]` might imply the client is preparing a payment for 26 sat; the client should instead order the list like so: `[2, 8, 8, 16, 64]` to mitigate this privacy leak to the mint.

## Swap to receive

Another useful case for the swap operation follows up the example above where `Alice` has swapped her `Proofs` ready to be sent to `Carol`. `Carol` can receive these `Proofs` using the same operation by using them as inputs to invalidate them and request new outputs from `Bob`. Only if `Carol` has redeemed new outputs, `Alice` can't double-spend the `Proofs` anymore and the transaction is settled. To continue our example, `Carol` requests a swap with input `Proofs` worth `[32, 8]` to receive new outputs (of an arbitrary distribution) with the same total amount.

## Example

**Request** of `Alice`:

```http
POST https://mint.host:3338/v1/swap
```

With the data being of the form `PostSwapRequest`:

```json
{
  "inputs": <Array[Proof]>,
  "outputs": <Array[BlindedMessage]>
}
```

All `inputs` and `outputs` of a swap **MUST** be of the same currency unit. The mint **MUST** reject a swap that mixes units (see [Error Codes][errors] `11009` and `11010`).

With curl:

```bash
curl -X POST https://mint.host:3338/v1/swap -d \
{
  "inputs":
    [
      {
        "amount": 2,
        "id": "009a1f293253e41e",
        "secret": "407915bc212be61a77e3e6d2aeb4c727980bda51cd06a6afc29e2861768a7837",
        "C": "02bc9097997d81afb2cc7346b5e4345a9346bd2a506eb7958598a72f0cf85163ea"
      },
      {
      ...
      }
    ],
  "outputs":
    [
      {
        "amount": 2,
        "id": "009a1f293253e41e",
        "B_": "02634a2c2b34bec9e8a4aba4361f6bf202d7fa2365379b0840afe249a7a9d71239"
      },
      {
      ...
      }
    ],
}
```

If successful, `Bob` will respond with a `PostSwapResponse`

```json
{
  "signatures": <Array[BlindSignature]>
}
```

## Mint-rerandomized outputs (V2)

An opt-in swap can authorize original blinded outputs while having the mint
reserve and sign fresh, derived points. This allows a pre-signed multi-party
swap to execute even if an original blinded output has already been signed
separately. This section specifies V2 secp256k1 swaps only; ordinary swaps,
melts, and V3 are unchanged.

A wallet opts in by adding `"rerandomize": true` to `PostSwapRequest`:

```json
{
  "inputs": "<Array[Proof]>",
  "outputs": "<Array[BlindedMessage]>",
  "rerandomize": true
}
```

The arrays above indicate the existing NUT-03 types; the string placeholders
are not valid proof or output data. An omitted `rerandomize` or an explicit
`false` requests an ordinary swap. An opted-in request **MUST** have inputs
locked with [NUT-11][11] `SIG_ALL` (including [NUT-14][14] HTLC conditions)
and **MUST** use the distinct authorization digest defined below. A mint
**MUST NOT** accept an ordinary `SIG_ALL` signature for an opted-in swap, or
silently execute it as an ordinary swap.

### Authorization of original outputs

For `rerandomize: true`, the `SIG_ALL` message commits to each original
blinded point through its SHA-256 hash. Define
`frame(x) = uint32_be(len(x)) || x`, where `len(x)` is the number of **bytes**
in `x`. The message starts with `frame(empty)` as a swap-context marker, then
contains for each input `frame(UTF8(secret))` and `frame(C_bytes)`, followed
by `frame(amount_bytes)` and the **unframed** 32-byte
`SHA256(B_bytes)` for each **original** output, in request order:

```text
message = frame(empty)
       || frame(UTF8(secret_0)) || frame(C_0) || ...
       || frame(amount_0) || SHA256(B_0) || ...
digest = TaggedSHA256("Cashu_SigAllRerandomized_v1", message)
```

`C_bytes` and `B_bytes` are raw 33-byte compressed secp256k1 points decoded
from their hex fields (not the UTF-8 hex strings). `SHA256(B_bytes)` hashes
exactly those original 33 bytes: it is neither a hash of the hexadecimal
text nor a hash of the mint's derived `B'_i`. As it is always 32 bytes, no
length prefix precedes the output hash. `amount_bytes` is the
minimal unsigned big-endian representation of the integer amount, with no
leading zero bytes; the integer zero encodes as the empty byte string.
`TaggedSHA256(tag, message)` means
`SHA256(SHA256(tag) || SHA256(tag) || message)`. The signer **MUST** sign the
32-byte `digest` directly as a BIP-340 Schnorr message; the verifier
**MUST NOT** hash it a second time. The frame for the empty context contributes
four zero bytes. The domain tag identifies the opted-in mode; the `rerandomize`
field itself is not another frame. Changing an input or the original output
order changes the authorization. The existing ordinary swap/melt `SIG_ALL`
encoding and `SIG_INPUTS` rules remain unchanged. Mints **MUST** verify this
exact transcript and **MUST NOT** accept an alternate output encoding as a
fallback.

See the [test vectors][03-tests] for the exact bytes and derived points.

### Derivation and issuance

The mint **MUST** generate an unpredictable fresh 32-byte `R` for this swap.
Let `tag` be the UTF-8 bytes of
`Cashu_OutputRerandomization_secp256k1_v1`. Starting at counter zero, compute
`candidate = TaggedSHA256(tag, R || uint32_be(counter))`; accept the first
candidate interpreted as a big-endian integer in `[1, n - 1]` as scalar `t`,
where `n` is the secp256k1 group order. Invalid or zero candidates **MUST**
be skipped. The same `t` **MUST** be used for every output in the swap.

For each original output point `B_i = Y_i + r_i G`, the mint computes:

```text
B'_i = B_i + t G
C'_i = a_i B'_i
```

Here `G` is the secp256k1 generator, `Y_i` is the proof's hash-to-curve
point, `r_i` is the wallet's original blinding factor, and `a_i` is the mint
key for that output's keyset and amount (`A_i = a_i G`). The mint **MUST**
reject duplicate original output points within the request, but **MUST**
check, reserve, and sign only the corresponding `B'_i` for output uniqueness.
A signature previously issued on an original `B_i` **MUST NOT** alone cause
the swap to fail. If addition produces the point at infinity, or a derived
point is already reserved or signed, the mint **MUST** abandon that `R` and
retry with fresh `R` or reject the swap without spending its inputs. Output
amounts, keyset IDs, and order remain the same; the returned signatures and
[NUT-09][09] records correspond to the derived points.

### Commit and lost-response recovery

The mint **MUST** commit the signatures and spent-input recovery value `R`
atomically, associating the same `R` with every spent input in the swap. It
**MUST NOT** reveal `R` while the swap is pending or if it fails. Only after
commit, `PostSwapResponse` includes `rerandomization_r`, the 32-byte `R`
encoded as exactly 64 lowercase hexadecimal characters:

```json
{
  "signatures": "<Array[BlindSignature]>",
  "rerandomization_r": "4242424242424242424242424242424242424242424242424242424242"
}
```

An ordinary swap response **MUST** omit `rerandomization_r`. A mint
**MUST** retain the committed `R` for as long as it supports recovery of the
associated signatures, and expose it through spent-input [NUT-07][07] state
and [NUT-17][17] proof-state notifications. After a lost response, the wallet
**SHOULD** check that all input states are `SPENT` and return the same `R`
before recovery; if any is still `PENDING`, it cannot infer completion. With
committed `R`, it can reconstruct each `B'_i` from its saved original output,
use [NUT-09][09] restore for the corresponding signatures, and unblind
normally:

```text
C_i = C'_i - t A_i
P_i = C_i - r_i A_i = C'_i - (r_i + t) A_i
```

`P_i` is an ordinary, transferable V2 proof. If the wallet needs a
transferable [NUT-12][12] DLEQ, its effective blinding factor is
`(r_i + t) mod n`; the mint's DLEQ on `(B'_i, C'_i)` does not change. The
wallet needs to retain its original output points and blinding factors to
perform lost-response recovery; this is not seed-only [NUT-13][13] recovery.
With independently sampled nonzero `r_i` and `t`, the chance that
`(r_i + t) mod n = 0` is approximately **2⁻²⁵⁶ per output** (at most about
`m / 2²⁵⁶` for `m` outputs). This is negligible in practice; the rare
representation case for an optional transferable DLEQ is addressed in
[NUT-12][12].

### Mint info setting

The mint **MUST** advertise `nuts["3"] = {"rerandomize": true}` through
[NUT-06][06] only when its active backend can atomically persist `R` for all
spent inputs and durably return it after a restart, together with the
associated [NUT-09][09] signatures. Absent or `false` means wallets
**MUST NOT** assume support or silently downgrade an opted-in pre-signed swap.
The setting denotes the complete V2 authorization, issuance, and recovery
behavior defined above, not merely ordinary NUT-03 support.
