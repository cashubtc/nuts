# NUT-20: Signature on Mint Quote

`mandatory`

`depends on: NUT-04, NUT-10`

---

This NUT defines signature-based authentication for mint quote redemption. When requesting a mint quote, clients provide a public key. The mint will then require a valid signature from the corresponding secret key to process the mint operation.

Quote locks are mandatory on keysets with version byte `02` or later: a mint **MUST** reject minting an unlocked quote onto such a keyset, and the lock signs the quote input's [NUT-10 input digest](10.md#the-transaction-transcript) ([NUT-04](04.md#nutroot-transactions-v3-keysets)). The pre-v3 message format is specified in [legacy NUT-20](legacy/20.md).

> [!CAUTION]
>
> A mint quote without a public key can be minted by anyone who knows the mint quote id.

## Mint quote

To request a mint quote, the wallet of `Alice` makes a `POST /v1/mint/quote/{method}` request where `method` is the payment method requested. We present an example with the `method` being `bolt11` here.

```http
POST https://mint.host:3338/v1/mint/quote/bolt11
```

The wallet of `Alice` includes the following `PostMintQuoteBolt11Request` data in its request:

```json
{
  "amount": <int>,
  "unit": <str_enum["sat"]>,
  "description": <str|null>, // Optional
  "pubkey": <str>
}
```

with the requested `amount`,`unit`, and `description` according to [NUT-04][04].

`pubkey` is the compressed secp256k1 public key (33 bytes, hex-encoded) that will be required for signature verification during the minting operation. The mint will only mint ecash after receiving a valid signature from the corresponding private key in the subsequent `PostMintRequest`.

> [!IMPORTANT]
>
> **Privacy:** To prevent the mint from being able to link multiple mint quotes, wallets **SHOULD** generate a unique public key for each mint quote request.

The mint `Bob` then responds with a `PostMintQuoteBolt11Response`:

```json
{
  "quote": <str>,
  "request": <str>,
  "unit":  <str_enum[UNIT]>,
  "amount_paid": <int>,
  "amount_issued": <int>,
  "updated_at": <int>,
  "state": <str_enum[STATE]>, // Deprecated, optional
  "expiry": <int>,
  "pubkey": <str>
}
```

The response is the same as the `bolt11` mint quote response in [NUT-23][23] except for `pubkey` which has been provided by the wallet in the previous request.

### Deterministic quote locking key derivation (v3 keysets)

For minting on keysets with version byte `02` or later, quote lock keys derive from the [NUT-13 V3 message](13.md#v3-message) with `derivation_type_byte` `0x04`, rejection sampled against `SECP256K1_N`. Every step is hardened, since a v3 quote lock key may be handed over ([NUT-04](04.md#nutroot-transactions-v3-keysets)), which rules out any watch-only equivalent.

The message frames an **empty** `keyset_id_bytes` (`u32_BE(0)`, no bytes): a quote is requested before any keyset is chosen, and the outputs of the [mint request](04.md#nutroot-transactions-v3-keysets) settle that afterwards.

The counter is a single wallet-wide cursor, independent of every [NUT-13][13] keyset counter. Wallets **MUST** advance it on every quote request: nothing detects a reused quote lock key the way a repeated `B_` detects a reused proof counter. To recover a lock key, derive candidates and match them against the quote's `pubkey`.

Request of `Alice` with curl:


## Signing the mint request

The signer commits to the quote and all `BlindedMessages` of the mint request through the [NUT-10 transaction transcript](10.md#the-transaction-transcript): the quote is an input, the outputs are outputs. The `signature` field carries the quote input's witness over the transaction digest, verified against the quote's `pubkey`: either a BIP-340 signature as 128 hex characters (key path) or a serialized [script-path witness](10.md#script-path) JSON string.

## Minting tokens

After requesting a mint quote and paying the request, the wallet proceeds with minting new tokens by calling the `POST /v1/mint/{method}` endpoint where `method` is the payment method requested (here `bolt11`).

```http
POST https://mint.host:3338/v1/mint/bolt11
```

The wallet `Alice` includes the following `PostMintBolt11Request` data in its request

```json
{
  "quote": <str>,
  "outputs": <Array[BlindedMessage]>,
  "signature": <str>
}
```

with the `quote` being the quote ID from the previous step and `outputs` being `BlindedMessages` as in [NUT-04][04].

`signature` is the quote's witness, as defined above.

The mint responds with a `PostMintBolt11Response` as in [NUT-04][04] if all validations are successful.

## Errors

If the wallet user `Alice` does not include a signature on the `PostMintBolt11Request` but did include a `pubkey` in the `PostMintBolt11QuoteRequest` then `Bob` **MUST** respond with an error. `Alice` **CAN** repeat the request with a valid signature.

See [Error Codes][errors]:

- `20008`: Mint quote with `pubkey` but no valid `signature` provided for mint request.
- `20009`: Mint quote requires `pubkey` but none given or invalid `pubkey`.
