# NUT-07: Token state check

`optional`

`used in: NUT-17, NUT-11, NUT-14`

---

With the token state check, wallets can ask the mint whether a specific proof is already spent and whether it is in-flight in a transaction. Wallets can also request the witness data that was used to spend a proof, or on v3 keysets a binding commitment to it.

### Token states

A proof can be in one of the following states

- A proof is `UNSPENT` if it has not been spent yet
- A proof is `PENDING` if it is being processed in a transaction (in an ongoing payment). A `PENDING` proof cannot be used in another transaction until it is `live` again.
- A proof is `SPENT` if it has been redeemed and its secret is in the list of spent secrets of the mint.

**Note:** Before deleting spent proofs from their database, wallets can check if the proof is `SPENT` to make sure that they don't accidentally delete an unspent proof. Beware that this behavior can make it easier for the mint to correlate the sender to the receiver.

**Important:** Mints **MUST** remember which proofs are currently `PENDING` to avoid reuse of the same token in multiple concurrent transactions. This can be achieved with for example mutex lock whose key is the `Proof`'s `Y`.

## Use cases

#### Example 1: Ecash transaction

When `Alice` prepares a token to be sent to `Carol`, she can mark these tokens in her database as _pending_. She can then, periodically or upon user input, check with the mint if the token is `UNSPENT` or whether it has been redeemed by `Carol` already, i.e., is `SPENT`. If the proof is not spendable anymore (and, thus, has been redeemed by `Carol`), she can safely delete the proof from her database.

#### Example 2: Lightning payments

If `Alice`'s melt operation takes a long time to complete (for example if she requests a very slow Lightning payment) and she closes her wallet in the meantime, the next time she comes online, she can check all proofs marked as _pending_ in her database to determine whether the payment is still in flight (mint returns `PENDING`), it has succeeded (mint returns `SPENT`), or it has failed (mint returns `UNSPENT`).

## Example

**Request** of `Alice`:

```http
POST https://mint.host:3338/v1/checkstate
```

With the data being of the form `PostCheckStateRequest`:

```json
{
  "Ys": <Array[hex_str]>,
}
```

Where the elements of the array in `Ys` are the hexadecimal representation of the compressed point `Y` of each `Proof` to check, computed with the hash-to-curve function of the proof's keyset (see [NUT-00][00]):

- For keysets with version byte `00` or `01`, `Y = hash_to_curve(secret)` is a compressed secp256k1 point (33 bytes / 66 hex characters).
- For keysets with version byte `02`, `Y = hash_to_curve_G1(secret)` is a compressed BLS12-381 G1 point (48 bytes / 96 hex characters); see [Pairing-based BDHKE (BLS12-381)](00.md#pairing-based-bls-blind-signatures).

**Response** of `Bob`:

`Bob` responds with a `PostCheckStateResponse`:

```json
{
  "states": [
    {
      "Y": <hex_str>,
      "state": <str_enum[STATE]>,
      "witness": <str|null>,
      "input_digest": <hex_str|null>,
      "commitment": <hex_str|null>,
    },
    ...
  ]
}
```

The elements of the `states` array MUST be returned in the same order as the corresponding `Ys` checked in the request.

- `Y` corresponds to the `Proof` checked in the request.
- `state` is an enum string field with possible values `"UNSPENT"`, `"PENDING"`, `"SPENT"`
- `witness` is the serialized witness data that was used to spend the `Proof`. On keysets with version byte `00` or `01`, it is present if the token has a [NUT-10][10] spending condition that requires a witness, such as P2PK ([NUT-11][11]) or HTLCs ([NUT-14][14]). On keysets with version byte `02`, it is present only for a `SPENT` proof spent through a leaf carrying `disclosure` mode `0x01`; otherwise it is null.
- `input_digest` is the 32-byte [NUT-10](10.md#the-transaction-transcript) input digest covered by a published v3 `witness`, and null otherwise.
- `commitment` is a binding commitment to the spend evidence (32 bytes hex), present for `SPENT` proofs on keysets with version byte `02` and null otherwise:

  ```
  witness_hash = SHA256(UTF8(witness))
  commitment   = tagged_hash("Cashu_SpendCommitment", Y || input_digest || witness_hash)
  ```

  `tagged_hash` and `input_digest` are [NUT-10](10.md#the-transaction-transcript)'s; `Y` contributes its raw compressed bytes, and `witness_hash` covers the UTF-8 bytes of the witness string value as received, not its JSON-escaped form. `Y` binds the commitment to the entry that returns it, `input_digest` the transaction and canonical input, and `witness_hash` the exact witness string. The spender can open the commitment to any holder of the proof by revealing the witness and `input_digest`. To prove how that digest was formed, the spender additionally reveals the TLV transcript: the verifier recomputes its transaction digest and the held proof's input id, then derives `input_digest`. Unopened, the commitment is not independent proof of a valid spend; it is bound data attached to the mint's `state` assertion.

  For a v3 spend through a leaf carrying `disclosure` mode `0x01`, the mint **MUST** return the exact witness string and `input_digest`, which together open the commitment; otherwise it **MUST NOT** return the witness, input digest, or transaction digest through this endpoint. A mint **MAY** retain any of them internally. `UNSPENT` and `PENDING` entries carry no commitment or v3 opening. See the [test vectors][tests] for a worked commitment and opening.

Legacy example (pre-v3), with curl:

**Request** of `Alice`:

```bash
curl -X POST https://mint.host:3338/v1/checkstate -H 'Content-Type: application/json' -d '{
  "Ys": [
    "02599b9ea0a1ad4143706c2a5a4a568ce442dd4313e1cf1f7f0b58a317c1a355ee"
  ]
}'
```

**Response** of `Bob`:

```json
{
  "states": [
    {
      "Y": "02599b9ea0a1ad4143706c2a5a4a568ce442dd4313e1cf1f7f0b58a317c1a355ee",
      "state": "SPENT",
      "witness": "{\"signatures\": [\"b2cf120a49cb1ac3cb32e1bf5ccb6425e0a8372affdc1d41912ca35c13908062f269c0caa53607d4e1ac4c8563246c4c8a869e6ee124ea826fd4746f3515dc1e\"]}"
    }
  ]
}
```

Where `Y` belongs to the provided `Proof` to check in the request, `state` indicates its state, and `witness` is the witness data that was potentially provided in a previous spend operation (can be empty).

The [NUT-06][06] `MintMethodSetting` indicates support for this feature:

```json
{
  "7": {
    "supported": true
  }
}
```
