# NUT-13: Deterministic Secrets

`optional`

`depends on: NUT-09`

---

In this document, we describe the process that allows wallets to recover their ecash balance with the help of the mint using a familiar 12 word seed phrase (mnemonic). This allows us to restore the wallet's previous state in case of a device loss or other loss of access to the wallet. The basic idea is that wallets that generate the ecash deterministically can regenerate the same tokens during a recovery process. For this, they ask the mint to reissue previously generated signatures using [NUT-09][09].

## Deterministic secret derivation

An ecash token, or a `Proof`, consists of a `secret` generated by the wallet, and a signature `C` generated by the wallet and the mint in collaboration. Here, we describe how wallets can deterministically generate the `secrets` and blinding factors `r` necessary to generate the signatures `C`.

The wallet generates a `seed` derived from a 12-word [BIP39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki) `mnemonic` seed phrase that the user stores in a secure place. The wallet uses the `seed`, to derive deterministic values for the `secret` and the blinding factors `r` for every new ecash token that it generates.

In order to do this, the wallet keeps track of a `counter_k` for each `keyset_k` it uses. The index `k` indicates that the wallet **MUST** keep track of a separate counter for each keyset `k` it uses. The wallet **MUST** keep track of multiple keysets for every mint it interacts with.

### Choosing the derivation

The secret derivation method depends on the keyset ID version the wallet derives secrets and blinding factors for.

- **Keyset V3** (keyset IDs starting with `02`): Use [V3 keysets](#v3-keysets-version-byte-02); the secret branch derives a private key whose public key is the secret (see [V3 Secret Key](#v3-secret-key)), and the blinding factor uses rejection sampling against [`BLS_FR_ORDER`](00.md#pairing-based-bls-blind-signatures) (see [V3 Blinding Factor](#v3-blinding-factor))
- **Keyset V2** (keyset IDs starting with `01`): Use [V2 keysets](#v2-keysets-version-byte-01)
- **Keyset V1 (deprecated)** (keyset IDs starting with `00`): Use [V1 keysets](#v1-keysets-version-byte-00-deprecated)

### Counter

The wallet starts with `counter_k := 0` upon encountering a new keyset and increments it by `1` every time it has successfully minted new ecash with this keyset. The wallet stores the latest `counter_k` in its database for all keysets it uses. Note that we have a `counter` (and therefore a derivation path) for each keyset `k`. We omit the keyset index `k` in the following of this document.

When encountering keysets with different versions, wallets **MUST** use the appropriate derivation method based on the keyset ID version and retain the existing `counter_k` value for each keyset to ensure consistent restore support across wallet implementations.

### V3 keysets (version byte `02`)

#### V3 message

For keysets with version byte `02`, the HMAC-SHA256 KDF is built as the following:

```
message_v3 = b"Cashu_KDF_HMAC_SHA256"
          || u32_BE(len(keyset_id_bytes)) || keyset_id_bytes
          || u64_BE(counter_k)
          || derivation_type_byte
          || u32_BE(attempt)
          || type_specific_suffix        # empty unless the type defines one
```

| Type   | Derives                                                 | Keyset id         | Suffix      | Counter |
| ------ | ------------------------------------------------------- | ----------------- | ----------- | ------- |
| `0x00` | internal private key `k`; the secret is `K = k*G`       | `keyset_id_bytes` | none        | proof   |
| `0x01` | blinding factor `r`                                     | `keyset_id_bytes` | none        | proof   |
| `0x02` | NUMS offset `u` for a script-only secret ([NUT-10][10]) | `keyset_id_bytes` | none        | proof   |
| `0x03` | self-owned leaf key `i` ([NUT-10][10])                  | `keyset_id_bytes` | `u32_BE(i)` | proof   |
| `0x04` | mint quote lock key ([NUT-20][20])                      | none              | none        | quote   |

Types `0x00`-`0x03` are components of one **proof allocation**: they share the keyset's proof counter, and one counter value describes one proof completely. Type `0x04` is a separate purpose with its own independent counter, since a quote exists before any proof and may mint none.

A keyset id of **none** is still framed, as `u32_BE(0)` with no bytes following: the field is never omitted. Type `0x04` takes none because a quote is requested before its keyset is chosen, and is defined in [NUT-20](20.md#deterministic-quote-locking-key-derivation-v3-keysets).

Purpose separation is carried by `derivation_type_byte`, not by a per-purpose BIP32 branch: the pre-v3 paths of [NUT-20][20] and [P2PK Derivation](#p2pk-derivation-pre-v3-keysets) are superseded, their non-hardened child indexes suiting keys that stay home rather than keys that travel. Quote locks keep the independent counter [NUT-20][20] already specifies, so a key meant to be published or handed over can never collide with one that must stay secret.

Sharing one counter makes uniqueness self-enforcing for `0x00`-`0x03`: reusing a counter regenerates the same `k` **and** the same `r`, so the blinded message `B_` repeats and mints refuse it as already signed. Every other component at that counter is protected by the same refusal. A quote lock (`0x04`) has no equivalent detector ([NUT-20](20.md#deterministic-quote-locking-key-derivation-v3-keysets)).

**Adding derivation types** Any future derivation type **MUST** keep the message parseable left to right without knowing its total length: every variable-length field length-framed. A type-specific suffix **MAY** carry length-framed fields of its own.

#### V3 secret key

V3 keysets are point-secret keysets ([NUT-10 Nutroot secrets](10.md#nutroot-secrets-v3-keysets)): the `0x00` branch output is not the secret itself but the internal **private key** `k`, and the secret is its compressed public key `K = k*G`, encoded as 66 lowercase hex characters.

Not every 32-byte digest is a valid secp256k1 private key, so the branch uses the same rejection sampling as the [V3 Blinding Factor](#v3-blinding-factor), here against `SECP256K1_N`. For `attempt = 0, 1, 2, …`, iterate until a valid key is produced:

```
message_v3 = <V3 message> with derivation_type_byte 0x00
k          = HMAC_SHA256(seed, message_v3)    # first digest in range [1, SECP256K1_N - 1]
secret     = lowercase_hex(K = k*G)           # 33-byte compressed point
```

The `u64` big-endian counter **MUST NOT** be narrowed to 31 bits (that is a BIP-32 limit, not relevant with HMAC_SHA256). Every key comes straight from the seed independently: learning one reveals nothing about any other, which is the hardening [NUT-10](10.md#key-uniqueness) requires of keys that travel.

#### V3 blinding factor

The V3 **blinding factor uses rejection sampling** against [`BLS_FR_ORDER`](00.md#pairing-based-bls-blind-signatures) instead of modular reduction. This matches the uniformity property used by NUT-00 batch weight derivation; modular reduction would introduce a ~7.5% statistical bias because `BLS_FR_ORDER ≈ 0.45 · 2^256`.

For `attempt = 0, 1, 2, …`, iterate until a valid scalar is produced:

```
message_v3 = <V3 message> with derivation_type_byte 0x01
hmac_digest = HMAC_SHA256(seed, message_v3)
x = OS2IP(hmac_digest)
if x == 0 or x >= BLS_FR_ORDER:
    continue   # try next attempt
blinding_factor = hmac_digest        # 32 bytes; equals OS2IP⁻¹(x) since x < 2^256
break
```

`attempt` is the unsigned 32-bit big-endian retry counter of the [V3 message](#v3-message), common to every derivation type.

`BLS_FR_ORDER` is defined in [NUT-00 (Pairing-based BDHKE)](00.md#pairing-based-bls-blind-signatures).

#### V3 NUMS offset

A script-only secret offsets the NUMS point, `K = H + u*G` ([NUT-10](10.md#bare-empty-tweaked-and-script-only-secrets)). Deriving `u` from the proof's own counter ties it to the same allocation as the secret, so it inherits the uniqueness the `B_` refusal enforces. Rejection sampling against `SECP256K1_N` as for the secret key, with `derivation_type_byte` `0x02`.

`u` is disclosed in spend info regardless, so deriving it buys uniqueness, not secrecy: a wallet that does not derive deterministically **MAY** use a fresh random scalar.

#### V3 leaf keys

A wallet's **own** leaf keys ([NUT-10](10.md#condition-leaves)) derive from the proof's counter with `derivation_type_byte` `0x03` and an index suffix `u32_BE(i)`, rejection sampled against `SECP256K1_N`. Keys belonging to other parties (a co-signer, an escrow agent) are their static keys and do not derive from here.

`i` has no canonical meaning and **MUST NOT** be read from a leaf's position: transmitted leaf order is not committed ([NUT-10](10.md#receive-time-verification)). To recover, derive candidates for `i = 0, 1, 2, …` and match them against the tree's keys **by value**, as [NUT-28][28] does for slot recovery. A proof cannot carry more than 255 leaf keys ([NUT-28][28] slot cap), which bounds the scan.

Deriving leaf keys does not make a locked proof seed-recoverable: the tree itself (leaf types, timelocks, hashes) is wallet data, as is `E` for a receiver-keyed proof. What it removes is the need to back up the keys **alongside** the tree, and it makes their uniqueness structural.

### V2 keysets (version byte `01`)

#### V2 message

For keysets with version byte `01`, the HMAC-SHA256 KDF is built as the following:

1. `message = b"Cashu_KDF_HMAC_SHA256" || keyset_id_bytes || counter_k_bytes || derivation_type_byte`, where:
   - `"Cashu_KDF_HMAC_SHA256"` is the domain separation or purpose string, encoded to bytes as UTF-8.
   - `keyset_id_bytes` are the raw bytes of `keyset_id` (hex decoded).
   - `counter_k_bytes` is the counter encoded as an unsigned 64-bit integer in big-endian format.
   - `derivation_type_byte` is exactly 1 byte specifying the type of derivation required:
     - `0x00` for secrets
     - `0x01` for blinded messages
2. `hmac_digest = HMAC_SHA256(seed, message)`, where `HMAC_SHA256` is the [hash-based message authentication code](https://en.wikipedia.org/wiki/HMAC) using SHA-256 as the hashing algorithm.
3. `secret = hmac_digest` and `blinding_factor = hmac_digest % N`, where `N = SECP256K1_N`. Reject `blinding_factor == 0` (astronomically unlikely).

This message needs no length framing: `keyset_id_bytes` is its only variable-length field and every other field is a fixed-width suffix, so the split into fields is unique. V3 frames it explicitly instead, because V3 adds per-type suffixes.

### V1 keysets (version byte `00`, deprecated)

> [!NOTE]
> This derivation method is used for keysets with version `00` (legacy keysets).
> Wallets **MUST** use this method when working with keysets that have IDs starting with `00`.

[BIP32](https://en.bitcoin.it/wiki/BIP_0032) derivation paths are used.
The derivation path depends on the [keyset ID][02] of `keyset_k`, and the `counter_k` of that keyset.

- Purpose' = `129372'` (UTF-8 for 🥜)
- Coin type' = Always `0'`
- Keyset id' = Keyset ID represented as an integer (`keyset_k_int`)
- Coin counter' = `counter'` (this value is incremented)
- `secret` or `r` = `0` or `1`

`m / 129372' / 0' / keyset_k_int' / counter' / secret||r`

This results in the following derivation paths:

```
secret_derivation_path = `m/129372'/0'/{keyset_k_int}'/{counter_k}'/0`
r_derivation_path = `m/129372'/0'/{keyset_id_k_int}'/{counter_k}'/1`
```

Here, `{keyset_k_int}` and `{counter_k}` are the only variables that can change. `keyset_id_k_int` is an integer representation (see below) of the keyset ID the token is generated with. This means that the derivation path is unique for each keyset. Note that the coin type is always `0'`, independent of the unit of the ecash.

> [!NOTE]
> For examples, see the [test vectors][tests].

#### Keyset ID to integer mapping (deprecated)

> [!CAUTION]
> This mapping is deprecated and unsafe to use due to its small keyspace.

The integer representation `keyset_id_int` of a keyset is calculated from its [hexadecimal ID][02] which has a length of 8 bytes or 16 hex characters. First, we convert the hex string to a big-endian sequence of bytes. This value is then modulo reduced by `2^31 - 1` to arrive at an integer that is a unique identifier `keyset_id_int`. Keyset IDs with version prefix `01` **MUST** be shortened to the first 8 bytes before conversion.

Example in Python:

```python
keyset_id_int = int.from_bytes(bytes.fromhex(keyset_id_hex), "big") % (2**31 - 1)
```

Example in JavaScript:

```javascript
keysetIdInt = BigInt(`0x${keysetIdHex}`) % BigInt(2 ** 31 - 1);
```

### P2PK derivation (pre-v3 keysets)

Wallets are able to generate private keys in a deterministic way to have proofs locked to them. [NUT-11][11] P2PK applies to keysets with version byte `01` or lower; v3 keysets express the same locks as [NUT-10][10] condition leaves.

The following BIP32 derivation path for derivation of the key: `m/129373'/10'/0'/0'/{counter}`:

- 129373': Purpose picked for P2PK derivation.
- 10': Account for generating private keys for usage in P2PK.
- `{counter}` is an incrementing, non-hardened BIP32 child index.

This will allow wallets to swap proof that are still locked to a public key during a restore process.

## Code examples

### Versioned secret derivation code

Below are code examples with keyset version-dependent derivation.

Python:

```python
import hmac
import hashlib

# secp256k1 scalar field (group) order
SECP256K1_N = int(
    "FFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141", 16
)
# BLS12-381 Fr (G1 group) order; see NUT-00 Pairing-based BDHKE (BLS12-381)
BLS_FR_ORDER = 52435875175126190479447740508185965837690552500527637822603658699938581184513

def derive_secret_and_r(seed: bytes, keyset_id: str, counter_k: int):
    """
    Derive secret and blinding factor using the appropriate method based on keyset version.
    """
    keyset_version = keyset_id[:2]

    if keyset_version == "00":
        return derive_secret_and_r_bip32(seed, keyset_id, counter_k)
    elif keyset_version == "01":
        return derive_secret_and_r_hmac_v2(seed, keyset_id, counter_k)
    elif keyset_version == "02":
        return derive_secret_and_r_hmac_v3(seed, keyset_id, counter_k)
    else:
        raise ValueError(f"Unsupported keyset version: {keyset_version}")

def _base_message(keyset_id: str, counter_k: int) -> bytes:
    return b"Cashu_KDF_HMAC_SHA256" + bytes.fromhex(keyset_id) + counter_k.to_bytes(8, 'big')

def _base_message_v3(keyset_id: str, counter_k: int) -> bytes:
    kid = bytes.fromhex(keyset_id)
    return (b"Cashu_KDF_HMAC_SHA256"
            + len(kid).to_bytes(4, 'big') + kid          # framed: the one variable-length field
            + counter_k.to_bytes(8, 'big'))

def derive_secret_and_r_hmac_v2(seed: bytes, keyset_id: str, counter_k: int):
    """V2 (secp256k1) HMAC-SHA256 derivation."""
    base = _base_message(keyset_id, counter_k)
    secret = hmac.new(seed, base + b"\x00", hashlib.sha256).digest()
    digest = hmac.new(seed, base + b"\x01", hashlib.sha256).digest()
    r = int.from_bytes(digest, "big") % SECP256K1_N
    if r == 0:
        raise RuntimeError("Derived invalid blinding scalar r == 0")
    return secret, r

def derive_secret_and_r_hmac_v3(seed: bytes, keyset_id: str, counter_k: int):
    """V3 (BLS12-381) HMAC-SHA256 derivation. Rejection sampling on both branches: secret key against SECP256K1_N, blinding factor against BLS_FR_ORDER."""
    base = _base_message_v3(keyset_id, counter_k)
    # Secret branch: first digest that is a valid secp256k1 private key.
    for attempt in range(1 << 16):
        msg = base + b"\x00" + attempt.to_bytes(4, "big")
        k = int.from_bytes(hmac.new(seed, msg, hashlib.sha256).digest(), "big")
        if k == 0 or k >= SECP256K1_N:
            continue
        secret = compressed_pubkey_hex(k)  # K = k*G, 33 bytes, lowercase hex
        break
    else:
        raise RuntimeError("V3 secret key derivation failed")
    # Blinding factor: rejection sampling, append u32_BE(attempt) until 0 < x < BLS_FR_ORDER.
    for attempt in range(1 << 16):
        msg = base + b"\x01" + attempt.to_bytes(4, "big")
        x = int.from_bytes(hmac.new(seed, msg, hashlib.sha256).digest(), "big")
        if x == 0 or x >= BLS_FR_ORDER:
            continue
        return secret, x
    raise RuntimeError("V3 blinding factor derivation failed")

def derive_secret_and_r_bip32(seed: bytes, keyset_id: str, counter_k: int):
    """
    Legacy BIP32 derivation for keyset version 00
    """
    # Convert seed to mnemonic and derive master key
    bip32 = BIP32.from_seed(seed)

    # Calculate keyset_id_int for BIP32 derivation path
    keyset_id_int = int.from_bytes(bytes.fromhex(keyset_id), "big") % (2**31 - 1)

    # Derive secret and r using BIP32 paths
    secret_path = f"m/129372'/0'/{keyset_id_int}'/{counter_k}'/0"
    r_path = f"m/129372'/0'/{keyset_id_int}'/{counter_k}'/1"

    secret = bip32.get_privkey_from_path(secret_path)
    r = bip32.get_privkey_from_path(r_path)

    return secret, r
```

import * as crypto from "crypto";
// secp256k1 scalar field (group) order
const SECP256K1_N = BigInt(
  "0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141",
);
// BLS12-381 Fr (G1 group) order; see NUT-00 Pairing-based BDHKE (BLS12-381)
const BLS_FR_ORDER = BigInt(
  "52435875175126190479447740508185965837690552500527637822603658699938581184513",
);

function deriveSecretAndR(seed: Buffer, keysetId: string, counterK: number) {
  const keysetVersion = keysetId.substring(0, 2);
  if (keysetVersion === "00")
    return deriveSecretAndRBip32(seed, keysetId, counterK);
  if (keysetVersion === "01")
    return deriveSecretAndRHmacV2(seed, keysetId, counterK);
  if (keysetVersion === "02")
    return deriveSecretAndRHmacV3(seed, keysetId, counterK);
  throw new Error(`Unsupported keyset version: ${keysetVersion}`);
}

function baseMessage(keysetId: string, counterK: number): Buffer {
  const counterBuf = Buffer.alloc(8);
  counterBuf.writeBigUInt64BE(BigInt(counterK));
  return Buffer.concat([
    Buffer.from("Cashu_KDF_HMAC_SHA256"),
    Buffer.from(keysetId, "hex"),
    counterBuf,
  ]);
}

function baseMessageV3(keysetId: string, counterK: number): Buffer {
  const kid = Buffer.from(keysetId, "hex");
  const kidLen = Buffer.alloc(4);
  kidLen.writeUInt32BE(kid.length); // framed: the one variable-length field
  const counterBuf = Buffer.alloc(8);
  counterBuf.writeBigUInt64BE(BigInt(counterK));
  return Buffer.concat([
    Buffer.from("Cashu_KDF_HMAC_SHA256"),
    kidLen,
    kid,
    counterBuf,
  ]);
}

function hmacSha256(seed: Buffer, msg: Buffer): Buffer {
  return crypto.createHmac("sha256", seed).update(msg).digest();
}

function deriveSecretAndRHmacV2(
  seed: Buffer,
  keysetId: string,
  counterK: number,
) {
  const base = baseMessage(keysetId, counterK);
  const secret = hmacSha256(seed, Buffer.concat([base, Buffer.from([0])]));
  const digest = hmacSha256(seed, Buffer.concat([base, Buffer.from([1])]));
  const r = BigInt("0x" + digest.toString("hex")) % SECP256K1_N;
  if (r === 0n) throw new Error("Derived invalid blinding scalar r == 0");
  return { secret, r };
}

function deriveSecretAndRHmacV3(
  seed: Buffer,
  keysetId: string,
  counterK: number,
) {
  const base = baseMessageV3(keysetId, counterK);
  const attempts = (branch: number) =>
    function* () {
      for (let attempt = 0; attempt < 1 << 16; attempt++) {
        const attemptBuf = Buffer.alloc(4);
        attemptBuf.writeUInt32BE(attempt);
        yield hmacSha256(
          seed,
          Buffer.concat([base, Buffer.from([branch]), attemptBuf]),
        );
      }
    };
  // Secret branch: first digest that is a valid secp256k1 private key.
  let secret: string | undefined;
  for (const digest of attempts(0)()) {
    const k = BigInt("0x" + digest.toString("hex"));
    if (k === 0n || k >= SECP256K1_N) continue;
    secret = compressedPubkeyHex(k); // K = k*G, 33 bytes, lowercase hex
    break;
  }
  if (!secret) throw new Error("V3 secret key derivation failed");
  // Blinding factor: rejection sampling until 0 < x < BLS_FR_ORDER.
  for (const digest of attempts(1)()) {
    const x = BigInt("0x" + digest.toString("hex"));
    if (x === 0n || x >= BLS_FR_ORDER) continue;
    return { secret, r: x };
  }
  throw new Error("V3 blinding factor derivation failed");
}

function deriveSecretAndRBip32(
  seed: Buffer,
  keysetId: string,
  counterK: number,
) {
  // Legacy BIP32 derivation for version 00
  // Implementation would use BIP32 library (e.g., bip32, bitcoinjs-lib)
  // Calculate keyset_id_int for BIP32 derivation path
  const keysetIdInt = BigInt(`0x${keysetId}`) % BigInt(2 ** 31 - 1);

  // This is pseudocode - actual implementation depends on BIP32 library
  const secretPath = `m/129372'/0'/${keysetIdInt}'/${counterK}'/0`;
  const rPath = `m/129372'/0'/${keysetIdInt}'/${counterK}'/1`;

  // const secret = bip32.derivePath(secretPath).privateKey;
  // const r = bip32.derivePath(rPath).privateKey;

  // Return placeholder for demonstration
  throw new Error(
    "BIP32 derivation requires additional library implementation",
  );
}

## Restore from seed phrase

Using deterministic secret derivation, a user's wallet can regenerate the same `BlindedMessages` in case of loss of a previous wallet state. To also restore the corresponding `BlindSignatures` to fully recover the ecash, the wallet can either requests the mint to re-issue past `BlindSignatures` on the regenerated `BlindedMessages` (see [NUT-09][09]) or by downloading the entire database of the mint (TBD).

The wallet takes the following steps during recovery:

1. Determine the keyset version from the keyset ID
2. Generate `secret` and `r` from `counter` and `keyset` using the appropriate derivation method:
   - For keyset version `00`: Use legacy BIP32 derivation
   - For keyset version `01`: Use HMAC-SHA256 derivation with `SECP256K1_N` reduction
   - For keyset version `02`: Use HMAC-SHA256 derivation with the [V3 Secret Key](#v3-secret-key) branch (the secret is the point `K = k*G`) and rejection sampling against [`BLS_FR_ORDER`](00.md#pairing-based-bls-blind-signatures) for `r` (see [V3 Blinding Factor](#v3-blinding-factor))
3. Generate `BlindedMessage` from `secret`
4. Obtain `BlindSignature` for `secret` from the mint
5. Unblind `BlindSignature` to `C` using `r`
6. Restore `Proof = (secret, C)`
7. Check if `Proof` is already spent

### Generate `BlindedMessages`

To generate the `BlindedMessages`, the wallet starts with a `counter := 0` and, for each increment of the `counter`, generates a `secret` and `r` using the appropriate derivation method based on the keyset version.

**For keyset version `00` (legacy):**

```python
secret = bip32.get_privkey_from_path(secret_derivation_path).hex()
r = self.bip32.get_privkey_from_path(r_derivation_path)
```

**For keyset version `01` (HMAC-SHA256):**

```python
secret, r = derive_secret_and_r_hmac_v2(seed, keyset_id, counter)
```

**For keyset version `02` (HMAC-SHA256 with V3 secret key and rejection sampling):**

```python
secret, r = derive_secret_and_r_hmac_v3(seed, keyset_id, counter)
```

For version `02`, restoring the `secret` also restores its private key `k`, so a restored key-path proof is immediately spendable. Script trees, random keys, and ephemerals ([NUT-10 spend info](10.md#spend-info)) are wallet data, not seed-derivable, and must be backed up separately.

> [!NOTE]
> For examples, see the [test vectors][tests].

Using the `secret` string and the private key `r`, the wallet generates a `BlindedMessage`. The wallet then increases the `counter` by `1` and repeats the same process for a given batch size. It is recommended to use a batch size of 100.

The user's wallet can now request the corresponding `BlindSignatures` for theses `BlindedMessages` from the mint using the [NUT-09][09] restore endpoint or by downloading the entire mint's database.

### Generate `Proofs`

Using the restored `BlindSignatures` and the `r` generated in the previous step, the wallet can [unblind][00] the signature to `C`. The triple `(secret, C, amount)` is a restored `Proof`.

### Check `Proofs` states

If the wallet used the restore endpoint [NUT-09][09] for regenerating the `Proofs`, it additionally needs to check for the `Proofs` spent state using [NUT-07][07]. The wallet deletes all `Proofs` which are already spent and keeps the unspent ones in its database.

### Restoring batches

Usually, the user won't remember the last state of `counter` when starting the recovery process. Therefore, wallets need to know how far they need to increment the `counter` during the restore process to be confident to have reached the most recent state.

The following approach is recommended:

- Set `counter = 0`
- Select key derivation function:
  - `00`: legacy
  - `01`: HMAC-SHA256 with `SECP256K1_N` reduction
  - `02`: HMAC-SHA256 with `BLS_FR_ORDER` rejection sampling
- Restore `Proofs` in batches of 100, and increment `counter`
- Repeat restore until three consecutive batches are returned empty
- Reset `counter` to the value at the last successful restore + 1

Wallets restore `Proofs` in batches of 100. The wallet starts with a `counter=0` and increments it for every `Proof` it generated during one batch. When the wallet begins restoring the first `Proofs`, it is likely that the first few batches will only contain spent `Proofs`. Eventually, the wallet will reach a `counter` that will result in unspent `Proofs` which it stores in its database. The wallet then continues to restore until _three successive batches are returned empty by the mint_. This is to be confident that the restore process did not miss any `Proofs` that might have been generated with larger gaps in the `counter` by the previous wallet that we are restoring.
