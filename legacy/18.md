# NUT-18 (legacy): the nut10 locking option

`legacy`

> The `nut10` payment request option requests a pre-v3 [well-known JSON Secret](10.md#well-known-secret) lock. The current specification is [NUT-18](../18.md).

---

## Locking conditions

The payment request can include _optional_ locking conditions the payee requires from the payer. For example, the payee might require a P2PK-locked token so that they can receive payments offline.

The `nut10` field specifies the payee's requested locking condition as a `NUT10Option` object. Its elements are derived from NUT-10's [well-known secret](10.md#well-known-secret). The `NUT10Option` is defined as follows:

```json
{
  "k": str,
  "d": str,
  "t": Array[Array[str, str]] <optional>
}
```

- `k`: NUT-10 secret kind,
- `d`: NUT-10 secret data,
- `t`: optional NUT-10 payment tags

> [!IMPORTANT]
> The payee must validate the incoming tokens themselves in order to decide whether they can accept the payment. This includes checking the `dleq` proof ([NUT-12](12.md)) and whether the token includes a long-enough timelock to satisfy the payee.

## Transition: carrying `nut10` beside `nutroot`

A request MAY carry `nut10`, [`nutroot`](../18.md), or both. Attaching `nut10` alongside `nutroot` offers one condition in both encodings so payers that predate v3 can still pay: such a payer follows `nut10`, and a payer paying from a keyset with version byte `02` or later MUST follow `nutroot`. A payee who publishes both MUST accept payment under either; whether the two encode the same condition is the payee's own responsibility, and only the payee is exposed if they differ.
