# NUT-16: Binary fountain test vectors

These vectors accompany the [binary fountain profile](../16.md). The machine-readable inputs and expected outputs are in [16-vectors.json](16-vectors.json). Hexadecimal strings represent bytes; they are not the QR payload encoding.

## Vector format

Each transfer specifies the message bytes, the maximum fragment length `C`, derived dimensions, message CRC-32, and complete frames. `indexes` lists the zero-based source fragments selected for that sequence; their order does not affect XOR. `data_hex` includes padding where present. `frame_hex` includes both the header and trailing frame checksum.

| Transfer             | Message bytes | Fragment count | Fragment bytes | Message CRC-32 | Scope             |
| -------------------- | ------------- | -------------- | -------------- | -------------- | ----------------- |
| `single-binary`      | 3             | 1              | 3              | `e9c0aed4`     | Framing only      |
| `padded-multipart`   | 17            | 4              | 5              | `2c183a19`     | Framing only      |
| `synthetic-v4-token` | 162           | 3              | 54             | `a0486a70`     | V4 token transfer |

The first two messages exercise arbitrary binary input at the fountain layer. They are not valid Cashu tokens and MUST fail token validation if presented as completed wallet transfers. The third contains a structurally valid, synthetic V4 token; its proof is not mint-issued or spendable. `token_text` is the expected canonical unpadded text representation after reconstruction.

For example, the first single-fragment frame is:

```text
43465031 00000001 00000001 00000003 e9c0aed4 0080ff d55abde9
```

The spaces above are explanatory only. The frame has 27 bytes, including three message bytes and 24 bytes of overhead.

## Positive checks

1. Verify the CRC check value for ASCII `123456789`.
2. Partition each message using its supplied maximum fragment length and verify every selected index, fragment and full frame byte-for-byte.
3. Reconstruct from the first `N` systematic frames, including reversed delivery order and duplicates.
4. Discard all systematic frames and reconstruct using `mixed_only_recovery_sequences`. These are sufficient input sets, not a required completion time for every decoder. A decoder that needs additional equations can receive the remaining supplied frames or subsequent frames generated by the same algorithm.
5. Verify the sequence `0xffffffff` vector without incrementing it to zero.
6. For the token case, verify that removing `crawB` and base64url-encoding the remaining CBOR bytes produces `token_text` exactly.

## Negative checks

Each `invalid_frames` entry contains a complete negative input and the stage at which it fails. `reject_at: frame` means the envelope, CRC or dimensions are invalid. `reject_at: message` means its frame checksum is valid but the reconstructed message checksum fails. A failed input MUST NOT result in a completed wallet transfer.

The fixtures cover an unknown version, sequence zero, zero and excessive fragment counts, zero and excessive message lengths, impossible dimensions, an empty last fragment, a corrupt frame checksum, a valid frame checksum with a corrupt message, and a truncated header. Except for the deliberately corrupt CRC and truncated-header cases, frame CRCs have been recomputed so that the intended rule is exercised.

Additional state checks:

- A malformed first frame must not select the active transfer.
- After accepting one frame, a valid frame from another transfer must not be mixed into its equations.
- Repeated copies of a frame must not count as independent information.
- An inconsistent equation or final checksum failure must not return a token.
- A correct fountain checksum on a reconstructed non-token payload must not bypass NUT-00 parsing.

## QR mapping checks

Encode each `frame_hex` value as its decoded bytes in one QR byte-mode segment. Scan it and verify exact byte equality before feeding it to the fountain decoder. For these fixtures, version 10-M is sufficient. This checks zero bytes and non-UTF-8 bytes as well as frame metadata. A valid decoder need not generate an identical QR image: masks and display parameters may differ.

Check that an implementation rejects the binary profile when extra segments, ECI, FNC1 or structured append are present. A scanner that exposes only decoded text cannot implement this profile. Existing text-token and UR dispatch should continue to work independently.

The vectors were checked against the prototype encoder and reader and a `@gandlaf21/bc-ur@1.1.12` encoder/reader through a CFP1 envelope adapter. Those implementations share the fragment chooser. A separate Python calculation also checked CRCs, fragment selection, frame bytes and mixed-only reconstruction. This is test-vector validation, not a claim of two production wallet implementations.

## Measurement supporting the rationale (informative)

The motivating experiment used Bun 1.3.14, `qrcode@1.5.4`, `jsqr@1.4.0`, `cbor-x@1.6.6`, and `@gandlaf21/bc-ur@1.1.12`. The table below records the 64-proof fixture's clean-image observations at 0% and 20% independently sampled frame loss. The metric is frames transmitted until exact token recovery, including dropped frames.

- All symbols were QR version 10-M (57 by 57 modules), rendered at four pixels per module with a four-module quiet zone and 32 additional pixels of white border: 324 by 324 pixels overall. Masks were selected automatically.
- Binary frames used byte mode; UR text was uppercased and used alphanumeric mode. Measured capacities were 213 bytes and 311 alphanumeric characters respectively. All envelopes and checksums counted against capacity. UR fragmentation reserved sequence-header capacity through sequence 10,000.
- The input had 64 synthetic proofs, a `https://mint.example` mint URL, unit `sat`, keyset ID `0011223344556677`, and no memo. Proof `i` (zero-based) had amount `2 ** (i % 10)`, secret equal to the lowercase SHA-256 hex digest of UTF-8 `poc-secret-${i}`, and signature `0279be667ef9dcbbac55a06295ce870b07029bfcdb2dce28d959f2815b16f81798`. It occupied 7,072 bytes as a binary token and 9,429 bytes as text. These are synthetic, unspendable proofs.
- The UR cases used the library's generic `ur:bytes` test container, which CBOR-wraps the supplied bytes. This experiment does not establish a production Cashu UR type. UR text carried the UTF-8 `cashuB` token; UR binary carried `crawB` and its CBOR body.
- The same seeded drop decisions were applied at each send index across schemes. Successful transfers had to recover the original token exactly. Deterministic image scans were cached across loss trials.

The binary control uses the library's fountain decoder inside the same CFP1 envelope. It separates some decoder effects from transport savings; the prototype uses Gaussian elimination.

The reduction relative to UR text is `100 * (1 - mean_CFP1_frames / mean_UR_text_frames)`: 49.3% without loss and 50.9% at 20% loss. Relative to UR carrying a binary token, the corresponding reductions are 33.3% and 35.2%.

These are headless image measurements and a small seeded sample, not phone-camera timing or a universal reduction. Other token sizes, QR sizes and loss patterns differ. Harsher combined synthetic image degradations in the broader experiment failed to recover within their frame budgets. The approximately 50% rationale refers specifically to the successful clean-image cases above, and includes changing both the inner token representation and the outer transport. Raw MUR CBOR frames in QR byte mode were not tested.
